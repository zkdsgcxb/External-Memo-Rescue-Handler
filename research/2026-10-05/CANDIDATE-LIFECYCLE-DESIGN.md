# 下一切片：计划、确认、候选准备、撤销与重入

日期：2026-10-05。**仅设计，等待协调者审阅，尚未实施。** 中文终端交互已经确认；公开支持范围尚未决定。本方案不添加发行版/精确内核白名单，不开始跨内核产物验证，不改变 C++ 恢复核心。

后续切片状态：其中的只读 `plan` 已获独立授权并实现，见 [只读计划验收](READONLY-PLAN.md)；下文的 `stage/cancel`、候选存储与确认后写入仍仅为待审设计。

## 最小验收结果

先闭合“用户看懂实际计划、确认保存候选、可撤销并安全重入”的小流程。第一项可实际准备的对象是**已有约定数据 DM 映射、但尚未登记的受支持 USB 数据卷**。复用现有身份和拓扑准入，候选保存在独立的 root 私有目录；不会进入当前启动流程消费的活动登记。

成功文案必须是：“配置候选已准备；尚未启用；仅重启不会生效。”这不是完整安装/启用旅程，也没有解决裸分区首次建图或根盘启动镜像安装。只有未来真正提交启动集成后，才可能出现“待重启”；这一步仍需另行审阅。不能为了制造完整流程而直接套用带启动副作用的旧函数。

候选保存不是恢复状态机：只有少量文件与操作记录，Guard 的准入、恢复和死亡接管仍是现有 C++ 唯一实现。计划内需用现有冷态身份准入，不能把 metadata-only 的 discover 结果直接当作可写依据。

## 对象与明确拒绝

| 当前对象 | 本切片计划与准备行为 |
| --- | --- |
| 已保护根盘及同组 shared LV | 核对现有 owner 和范围；返回“已有保护／无新增候选”或信息不足，不再登记、不开第二个控制器 |
| 已登记、正在维护的数据映射 | 显示已有登记/运行证据；一致时无变更，不借重新规划更新身份；异常则给具体阻碍 |
| 已有约定 DM 映射、尚未登记的数据卷 | 完整核验选定对象；允许保存候选登记，但不启用、不改现有映射 |
| 数据卷已挂在该 DM 上 | 仍须通过现有隔离准入；可准备符合条件的候选，但挂载与应用状态不变，尚未启动 Guard 就不能声称已保护 |
| 正在使用的裸分区 | 拒绝准备接入，说明需用户正常卸载后重新规划；不自动卸载、结束应用或在线改接 |
| 未挂载且没有稳定 DM 的裸分区 | 展示缺少映射创建生命周期的阻碍，本切片不生成看似可启用的登记；这是后续产品缺口 |
| 未保护根盘 | 只说明后续需匹配的可信保护镜像及启动计划；本切片不构建、不安装、不改启动项 |
| 系统盘未覆盖兄弟分区、整盘文件系统、额外 LVM/LUKS/多路径拓扑等 | 沿用当前准入拒绝；不扩大支持范围 |

已有映射的 UUID、几何或身份不合约定时不能“修好后继续”。完整核验只访问选中对象，不批量逐盘探测；不调用会标坏路径的 DM probe ioctl。身份检测失败、依赖不匹配或支持策略无法满足时，计划有 blockers，准备必须拒绝。

## 一个入口与三个动作

以下是生命周期拟定接口；目前仅 `plan` 已实现，其他动作不可执行：

- `manager plan --device <对象> [--json]`：无持久写入；解析受限设备意图，生成中文计划或版本化 JSON。
- `manager stage`：交互串起发现、编号选择、计划、明确确认，再准备候选。自动化为 `stage --device <对象> --expect-plan <SHA256>`；特权入口重新生成执行内容并与期望摘要核对。
- `manager cancel --operation <ID>`：只撤销未提交候选；交互展示将保留/删除的候选文件后确认，自动化也须携带该候选的计划摘要。

现有 `manager status` 可添加候选摘要区，保留原自动化字段；不混入“当前受保护设备”计数。用户没有确认、输入否、EOF 或 Ctrl-C 时零持久写入，也不为显示计划创建锁文件或操作目录。只使用 root 所有的固定安装入口执行特权流程，不从工作区 sudo 导入源码。

## 计划数据与确认边界

计划 schema 1 只包含固定字段，不接受外部命令或任意目标路径：

| 字段 | 内容 |
| --- | --- |
| `action`、`selected_object` | 候选登记动作、选定设备的核验身份、DM UUID 与卷级含义 |
| `scope` | 关联卷、挂载、共同恢复组，EFI/其他裸分区等明确例外 |
| `inputs` | 选定对象身份、boot ID、diskseq、映射表、挂载/swap/fstab，可信登记名单/内容、收据、包与匹配内核的摘要 |
| `proposed_outputs` | 固定候选文件类别及内容摘要；不使用调用者给出的输出路径 |
| `effects` | 本轮只保存哪些候选文件；未来启用仍需哪些步骤；当前系统不会因此受保护 |
| `blockers`、`unknowns` | 缺失的身份/候选/范围条件；阻碍存在时禁止 stage |
| `plan_digest` | 以上执行相关内容的规范化摘要，不含展示时间、随机 snapshot ID、doctor 脱敏 token 或随机操作 ID |

编号只在同一次终端交互快照中有效。`/dev/sdX` 仅作当次定位，计划绑定核验身份、DM UUID 及当次设备实例；重编号、拔插、diskseq 改变即拒绝旧确认并要求重新展示计划，不能自动拿新实例代替。

确认前不持锁。确认后复用 `manage.exclusive_control`，重新核验选中对象与输入并重算摘要；不一致则返回 `plan_changed`，不写候选、不静默更新确认内容。自动化的 `--expect-plan` 不是任意 JSON 执行许可；只接受受限意图并在可信代码中重建候选。

该锁只串行化本工具的合作式操作，不能阻止内核热插拔、旧版本进程或其他 root 修改。候选物化完成后再次核对所用输入；变化则记录未成功、保留可审阅现场，不把候选当成当前有效。未来真正提交启动配置前仍须最终核验，不能信任今天的 prepared 收据。

## 准备与存储

候选放在 **`/var/lib/ram-rescue-plans/operations/<ID>/`**，目录 0700、普通文件 0600、root 所有，沿用可信路径/禁止链接的访问方式。不能放进 `/var/lib/ram-rescue-manager/`：现有 `manager.install()` 只要 INSTALL 目录存在就拒绝，保存候选不能意外阻止首次安装。

操作目录只有固定成员：

- `plan.json`：用户确认的规范化计划。
- `candidate.json`：通过现有 `record_from_profile()` 生成的候选登记；去除 initial node/sysfs/diskseq 等不能持久登记的实例字段。
- `manifest.json`：文件摘要、输入指纹、所引用包/候选摘要。
- `operation.json`：操作 ID、计划摘要、`preparing / prepared / cancelled / failed_needs_review`、有限原因码。

当次设备实例约束仅放在计划输入，不混入可长期使用的登记。先写 `preparing`，使用现有原子文件写入与目录同步方式物化固定成员，核对摘要与输入后写 `prepared`。不依赖这个目录触发 udev、systemd 或启动镜像生成。

本切片不提供挂载策略写入，最多显示现有挂载及冲突；后续确需挂载候选时复用 `mounts.validate_plan/render_units`，不能猜测用户 fstab 意图。引用已有可信不可变包/镜像，不复制内核、initrd、工具归档或 VM 镜像。建议单操作最多 1 MiB、未撤销候选最多 16 个、历史小收据最多 256 个，超限明确停止并给出处理说明，不暗中删除旧记录。

## 撤销、失败与重入

| 情况 | 行为 |
| --- | --- |
| 相同意图/输入重复 stage | 核验已有 prepared 的固定成员和摘要，返回同一候选，不重复复制/备份 |
| `preparing` 残留，成员完整且输入仍吻合 | 在现有锁内核验后完成收据；不重放系统启用动作，因为候选操作根本不包含这些动作 |
| 成员缺失或输入已改变 | 拒绝沿用旧确认，记录 `failed_needs_review`；用户重新规划确认后生成新候选，不自动修补未知文件 |
| 撤销 prepared/preparing | 仅处理本操作拥有且摘要符合 manifest 的候选生成物，保留最小计划摘要、操作收据和失败信息 |
| 撤销重复执行 | 已 cancelled 且 cleanup_pending=false 时直接返回；pending=true 时继续受限清理，不生成新备份 |
| 遇到软链接、陌生成员、外部改动或摘要损坏 | 停止自动覆盖/删除并保留证据；不递归清理目录 |
| 重入 cancelled | 旧操作保持终态；按现状重新计划确认，生成新操作 ID，不能复活旧确认 |
| 候选曾被未来版本提交、或设备已有活跃变更 | 拒绝 candidate cancel，交给独立的停用/退出方案；不能把候选撤销当作运行系统回退 |

先持久化 `cancelled + cleanup_pending=true`，再清理 manifest 声明且摘要吻合的本操作成员，完成后持久化 `cleanup_pending=false`。已经清理掉的成员在重试时视为完成；若发现外部改动则保留并报告需审阅。这样即使写完取消收据、尚未开始清理就崩溃，重入仍能继续处理。所有共享不可变候选、设备数据、文件系统、活跃登记和日志不在清理范围内。崩溃后最多留下私有候选及小收据，不会留下半套生效中的 systemd/udev/启动配置。

已有 `uninstalled` 后重新 install 的缺口仍未解决：旧卸载保留 INSTALL，而旧安装拒绝该目录。这个切片只承诺**候选操作**的重入，不删除旧收据绕过安装器。真正停用、系统卸载和重装另做方案。

## 复用点与不能直接调用的旧路径

| 现有位置 | 采用方式 |
| --- | --- |
| `discovery.collect/format_text` | 发现与解释；不能直接拿结果作准入或计划摘要，因为含随机 token、缓存和未知项 |
| `admin.data.collect` | 选中约定数据映射的完整只读身份、环境、表与隔离核验；沿用现有超时和最终 revalidate，不另造判断器 |
| `admin.registry.record_from_profile/validate_record` | 唯一候选登记格式与校验 |
| `manage.exclusive_control`、`trusted_paths`、`host_files.atomic` | 合作锁、可信路径、小文件原子更新；补齐必要目录同步，不另造一套特权执行器 |
| `stage_inputs`、`install.validate`、`upgrade.unchanged` | 未来提交启动集成时复用可信封存/产物绑定/前后摘要思路；本切片不调用部署路径 |

`manage.prepare()` 是启动期 RAM 准备；`register()` 包含写活动登记、reload、RAM prepare、trigger 和启动控制器；`install()` 含 enable --now；`install-image` 会改 /boot 和 GRUB。它们都不能被候选 stage 包装后直接调用。根镜像 rollback 只接受完整、摘要一致的已安装记录，也不是任意候选取消器。

下一步代码可采用一个小的冷态候选模块，管理入口只负责交互/JSON 分发。不要改 Guard，不要为这个流程写驻留服务、通用工作流引擎或第二套恢复事务。

## 验收与后续门槛

针对性 fixture 测试先覆盖：确认前取消零写入；没有正确摘要拒绝；换盘/重编号/diskseq/表变化拒绝旧确认；登记、收据、包、内核或 fstab 变化失效；挂载裸分区、swap、额外层和同盘例外拒绝；重复 stage/cancel 幂等；每个持久写边界崩溃后明确重入；并发 stage/cancel 与现有登记/升级锁互斥；路径逃逸、链接、陌生文件、篡改摘要不覆盖或删除；候选配额与引用而非复制。

负面断言必须覆盖 DM mutation、mount/umount、服务 start/stop/enable、udev trigger、RAM prepare、活动 registry 和 /boot 写入均未发生。成功只叫“候选已准备”，不能叫 verified、待重启、当前已启用或恢复实验通过。
