# 管理入口、可信文件与冷态部署审阅

本轮对固定 root 管理入口、文件信任检查、保护镜像封存、离线包、RAM 环境、首次安装、升级、回退和统一管理命令做了独立代码审阅。重点是普通用户可写路径进入高权限流程、并发部署以及实际可达的升级/回退错误。审阅与回归均使用普通用户的临时目录；没有操作宿主 GRUB、initrd、服务或磁盘。

这是一轮范围明确的工程审阅，不是完整安全审计或不存在漏洞的证明。信任起点仍是管理员审阅并安装的包；本地 SHA256 不能认证发行者身份。本轮不试图限制已经具备 root 权限的管理者，也不对抗恶意内核。

## 发现并修正的实际问题

### 保护镜像升级和卸载曾可并发

旧 `upgrade.py` 独占状态目录上的 flock，但 `install.py` 的 rollback 没有取得同一把锁。普通临时树中已复现：一个流程持有升级锁时，真实 rollback 函数仍可恢复菜单、删除镜像和 hook，并写入 `removed` 收据。两个实际部署进程因此可能在旧收据核验后互相覆盖结果。

现在 `install.deployment_lock()` 是唯一实现。首次安装独占创建状态目录后，在备份、收据、引导菜单写入及异常清理期间持锁；升级直接复用；rollback 在读取任何收据前持锁。锁 FD 通过 `trusted_paths.open_directory` 校验完整路径各级的 owner、权限和非符号链接属性。rollback 的收据、镜像、菜单、hook 及备份也通过可信文件接口读取；备份读取有上限，恢复时使用已经校验的同一字节副本。

定向测试为 **12 项安装/回退 + 21 项升级**。新增测试使用独立 Python 子进程争用真实 flock：损坏收据在拿不到锁时不会被读取，升级和回退均不改变文件；首次安装在备份、收据提交后模拟 fsync 失败及清理阶段，另一个进程均拿不到锁。另验证可写父目录、状态目录符号链接，以及五类回退输入的可写权限/符号链接都被拒绝。所有临时测试树均为普通用户所有，测试只显式替换 root uid/路径 anchor，不放宽生产策略。

### 已安装的根盘登记命令曾沿用工作区输出假设

旧 `enroll-root` 把输出限定为源码目录旁的 `lab/work`。包安装到 `/usr/lib/ram-rescue-handler/<版本>/` 后，这个相对源码位置不再是用户工作区；文档示例同时缺少明确的身份来源。固定安装入口因此无法按文档完成登记。

现在使用 `--name` 在 `/var/lib/ram-rescue-enrollments/<名称>/` 建立独占、root 私有的记录；通过明确的 `--partition` 与预期 USB 序列，或已有可信身份文件确定对象。目录为 0700，三个导出文件为 0600；读取 boot 文件及写入目标均基于已核验的 FD。输出不写入用户可替换的工作区路径。普通用户需要构建时，由管理员只读输出 tar 流，普通用户的 tar 进程在工作区接收。

新登记接口有 9 项定向测试，原有登记/准入相关 11 项继续通过。最终普通 Ubuntu VM 场景另外使用真实 seed PV、真实内核和原 initrd，通过安装后的固定入口检查身份、三文件 SHA、私有权限、原引导文件与映射不变，以及标准 tar 流内容一致；实际结果以 [独立数据盘验收](STANDALONE-DATA.md) 对应的最终产物为准。

### 构建 bundle 不应经 root 入口写入工作区

`image-inputs` 模块同时提供普通用户的 `bundle` 和特权 `stage`。原先固定 root 入口也可以转入 `bundle`，以 root 身份在调用者指定的输出路径创建文件。虽然 `xb` 禁止覆盖已有文件，这仍与“普通用户构建、root 只封存已审阅输入”的职责不符。

现在 `bundle()` 在读取输入或创建输出之前拒绝 euid 0；普通用户构建接口保持原样，固定管理员入口只能实际执行 `stage`。新增拒绝测试确认不解析输入、不创建输出，封存与可信路径的 **16 项**定向测试通过。剩余入口的子命令参数也逐项核对：没有新增任意命令执行、网络下载或工作区 Python 导入路由。管理诊断导出是明确选择的本地私有报告输出，仍使用其独立的目录 FD、0600/0700、排他创建和路径替换检查。

## 核对的职责与边界

| 部件 | 本轮核对的契约 |
| --- | --- |
| `guard/admin_entry.py` | Python `-I` 固定入口；仅标准库 bootstrap；root 所有且不可由普通用户写入的整条目录链；选中的命令必须列入清单，随后核验清单文件 SHA |
| `guard/trusted_paths.py` | 逐级目录 FD、不跟随链接；普通单链接文件；owner/mode 检查；有界读取和读取期间变化检查 |
| `guard/stage_inputs.py` | 对用户 bundle 持有输入 FD，先复制到 root 私有目录并核对操作者独立记录的 SHA；仅允许四个定名、有限大小的普通文件；再核验 build、测试报告和当前安装源码 |
| `guard/package.py` | 无 maintainer scripts；离线安装不自动启用服务或改引导；代码与 RAM 归档共同决定管理版本；实验 sanitizer 运行时不会进入发行包 |
| `guard/ram_environment.py` | 比较完整 native 清单和 base 归档身份；拒绝已运行环境热替换；真实目录用作 systemd root；匹配的根盘环境通过 bind 复用；冷态只读固定单个 fstab |
| `guard/install.py` / `guard/upgrade.py` | 共用部署锁；镜像与源码/内核/VM 证据相符；不自动改普通默认入口；升级保留回退证据，异常恢复先核对实际落盘结果 |
| `guard/manage.py` | 管理与登记职责独立于 C++ 恢复状态机；冷升级必须先退出全部登记的数据映射和 controller，保留登记，只在下一启动启用新的 RAM 副本 |

可信配置 FD 规则不用于 `/dev`、`sysfs` 等内核动态路径；后者保留块设备类型、实例和身份准入检查。恢复循环没有加入 package 哈希、磁盘扫描或依赖版本查询；这些工作只发生在明确的管理/诊断调用中。

## 已有救援终端的独立更新边界

`upgrade-image` 只替换保护 initrd，**不会自动更新宿主的日志 unit**。新资源在离线包的 root 版本目录中，现有救援终端需要按 [可信安装说明](INSTALLATION-AND-TRUST.md#已有救援终端的日志服务冷更新) 完成资源清单核验、私有备份、drop-in 检查、SHA 对照及冷态复制；只 daemon-reload，不重启当前日志服务，下一次启动检查实际进程挂载限制。

这条流程保留现有救援账号与凭据，不调用旧的工作区 root 安装脚本，也不升级普通回退启动仍使用的旧 RAM 工具整包。旧整包与新限制组合的实机验收仍需单独完成。以上部署边界已明确记录，不以 VM 服务启动成功替代宿主冷启动验收。
