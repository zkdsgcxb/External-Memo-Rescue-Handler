日期：2026-09-25。对象：Ubuntu 6.8 内核、USB SSD、LVM/ext4 根系统及共享工作区。基线代码：`b06d7c7`。本文是一份带证据边界的路线决策，**不是实机部署批准或全故障容错证明**。

同日后续已补 Linux 7.0 与 multipath-tools 0.15 的九次隔离运行，见 [版本对照](VERSION-STUDY.md)。下文原实验的版本、哈希与观测保持原口径；新版结论分别标明，不能将旧记录视为新版本重跑。

## 1. 结论与推荐路线

建议保留上游 Linux 的 DM 数据路径，先明确可靠、可测的单一用户态路径管理合同；共同的事务边界补测与 multipathd 替代评估并行进行，避免先完善日后要删除的重复功能。**现阶段不建议把 USB 身份、PV/VG/LV 格式解析和应用恢复策略移入内核。** 本轮发现的是控制事务和证据不足的问题，尚未证明必须新增内核 DM target 才能解决。

具体决策：

1. **继续使用现成 dm-multipath 的 BIO 排队能力作为实验基线。** 它已经在完整 Ubuntu/LVM 根盘和真实 Git 负载上表现出可用性，但保护条件必须限定为符合路径重试语义的请求、可恢复设备状态和有限等待窗口。
2. **优先修复“恢复事务中途失败”的可收尾性，再扩大功能。** 本轮已实证：管理器在映射暂停后死亡，内核无路径超时不能自动解除 DM 暂停。此前“后台死了也总能在内核超时后释放”的表述过宽。
3. **先核对上游新版已提供的能力，再研究 multipathd 的有限用户态扩展；保留当前 Guard 作为对照。** 0.9.4 及后续 0.15 均在单 USB/LVM 数据卷上连续三次重接成功，普通调度也可运行；同标识空白替代盘反例在 0.15 仍存在，其身份合同不满足本项目严格准入要求。新版调度/checker 改进应直接复用，缺口才进入扩展。扩展是否划算，仍须比较维护量与全部 RAM/CPU 成本。不得让 Guard 与 multipathd 同时拥有同一张映射表。
4. **额外身份策略留在用户态，且必须在新路径进入活动映射前执行。** 如果标准配置足够，删除对应自写功能；若不够，先寻找可审计的用户态接入点或小补丁。不要用“先接回、随后检查”的旁路脚本补准入。
5. **只在获得最小内核问题复现后考虑内核/驱动补丁。** 例如确实缺少可恢复的事务接口、设备实例绑定能力，或某个 USB/UAS 驱动不能正确取消请求。修改点可能在驱动，不一定在 DM。
6. **根盘失联后仍保持完整系统存活是有条件目标。** 断电丢失设备已确认的易失缓存、介质错误、静默数据损坏、永久掉盘、内核死锁、RAM/OOM 故障不可能由路径重接一并解决。

## 3. 实际故障域与目标

### 3.1 本机与实验布局

本轮只读检查确认：

- `/` 是 USB SSD 第 3 分区上的 LVM/ext4 根 LV；`/workspace` 是同一 PV 上的另一个 LV。
- `/swap.img` 是根文件系统上的活动 8 GiB swap 文件。观测时使用量为 0，不能据此忽略未来内存压力下的依赖。
- 同盘 EFI 和 exFAT 分区有独立挂载，绕过当前 LVM 根卷保护范围。
- 当前 USB 存储使用 UAS。当前拓扑和 9 月 23 日事故时“经过 Hub”的用户记录分别保存，不能把任一时期拓扑当成另一期事实。

原事故缺少最后时刻的 USB/SCSI/ext4 日志；Hub、线材、供电、桥接固件、UAS、SSD 内部故障和重新枚举仍是待区分原因。**本项目已复现某一类重枚举问题，不等于追溯证明原事故根因。** [原始事件记录](../../ram-rescue-demo/incidents/2026-09-23-near-1100/README.md)

当前实验数据路径：

```text
Ubuntu / 应用 → ext4 → LVM LV → 稳定 DM multipath → USB 分区 → 虚拟 USB SSD
```

本轮标准 multipathd 对照采用的布局为：

```text
Ubuntu / 应用 → ext4 → LVM LV → multipath 的分区映射 → 整盘 multipath → USB SSD
```

这两个布局不是可随意互换的配置细节。EFI/exFAT 是否也进入稳定整盘的分区映射、启动时怎样避免裸分区和稳定分区被重复识别，必须单独设计。不能在已运行的真实根文件系统上试着“在线插一层”来代替启动集成。

### 3.2 目标分级

| 级别 | 承诺内容 | 当前证据 |
|---|---|---|
| G0 救援存活 | 根盘失联时，独立 RAM 诊断入口仍可用 | 多组 QEMU 正/负样本；实机安装验证不是本轮范围 |
| G1 路径连续 | 保留上层 DM/LV 设备，原盘重枚举后安全接回 | 已有 UAS/BOT 正样本 |

| G4 任意系统无感 | 桌面、数据库、网络会话、所有服务、所有故障均无影响 | 不作承诺；需按应用与故障域拆解 |

## 4. 必须修正的机制理解

### 4.1 DM 保护的是请求语义，不是“任何 EIO 都消失”

`multipath_end_io_bio()` 只对 `blk_path_error()` 归类的错误进入路径失效/重试处理；介质、保护等错误不应被无差别吞掉。文件系统、应用错误、设备掉电后的已确认缓存丢失也不是重排队可以撤销的。[K1][K2]

磁盘移除还有 `bdev_mark_dead`/文件系统 holder 通知路径，不能把“文件系统只能从失败 BIO 得知设备死亡”当作完整模型。保持顶层 DM 和文件系统挂载所绑定的设备对象稳定是设计条件；物理底盘死亡与直接移除顶层 DM 是不同故障。[K3]

### 4.2 地址相同不等于设备实例相同

节点名、sysfs 路径、major:minor 都不能单独充当永久设备身份。`diskseq`/`BLKGETDISKSEQ` 可帮助区分内核磁盘实例，但不证明磁盘内容是原盘；USB 序列号、WWID、PV UUID、分区 UUID、布局都各自回答不同问题。复制盘可能复制 UUID，廉价桥接可能缺失或复用标识。严格准入必须定义可信前提，不能写成“完整认证”。[K4][U2]

同时，拿住候选 fd 并核对 diskseq，也不自动证明最终 DM target 内部绑定了所期望的新对象。需要验证从候选实例到实际 target 的绑定过程，尤其是设备号复用；目前没有复现实证证明这里一定存在错误，也没有证据证明所有后端都安全。[内核研究](kernel-failures.md)

### 4.3 无路径超时不是端到端请求上限

请求已经交给下层驱动后，可能等待命令完成、SCSI 错误恢复或设备 reset。DM 还未收到路径失败时，无路径计时可能尚未启动。`dmsetup`/LVM 的进程超时也不能强制取消处于不可中断内核 I/O 的任务。[K5]

此外，`dm suspend --noflush` 仍可能等待已发出的请求完成。noflush 不等于“完全不等待任何 I/O”。[K6]

当前 Guard 设置的 `queue_if_no_path_timeout_secs` 是 dm-multipath 模块参数，不是每个 LV、每个请求的独立期限。扩大到多张 multipath 映射前，必须处理共享参数的配置所有权，不能让多个 Guard 互相覆盖它。[K1]

### 4.4 停止无路径排队不是全局禁止写入

`fail_if_no_path` 的含义是没有可用路径时不再无限排队，不是永久写栅栏。已有可用路径或已提交到下层的请求仍可能完成。当前 Guard 的 `expired` 是“不再自行接回”的策略状态，不能宣称它原子地取消了所有旧写入、永久阻止了任何后续写入。[K1]

应另外区分持续供电的链路失联与 SSD/桥接实际掉电。普通写请求可能已经向 DM 返回成功、离开重试队列，却仍停留在设备易失缓存中；掉电丢失后，重接再执行 flush 不能重建这些数据。身份/布局相同、没有观测到 EIO，也不足以证明沿用原挂载状态安全。需要明确设备缓存、flush/FUA、掉电保护及独占写入合同，并用真实断电实验验证。[D1]

如果产品要求“超过某时刻后绝不允许任何写请求落盘”，必须另行定义并验证栅栏、在途请求处理和设备复位语义；不能靠一个状态字段或 DM message 宣布完成。

## 6. 已有实验与本轮补测

### 6.1 现有正向证据

完整 Ubuntu Server 用户空间、PID 1 为 systemd，真实根文件系统位于故障 USB/LVM 路径；不是只在健康系统上拔掉一个数据盘。Linux v6.8 源码仓库实际克隆，验证 Git 退出码、HEAD、fsck、工作树和进程身份；同时执行追加写入+fsync。相关结果保存在 [Ubuntu 实验](../../lab/UBUNTU.md)。

优化版 Guard：健康 CPU 平均单核 `0.104%`，约 100 ms 窗口峰值 `1.512%`；每秒约 100 个合成事件时平均 `0.889%`、峰值 `2.181%`。RSS `14.63 MiB` 仅为父进程。该结果来自单次 KVM 采样，不是任意硬件的保证。[监视验收](../../lab/results/2026-09-24-monitor.json)

### 6.2 新实验 E-STALLED：下层慢请求不触发无路径计时

本节与 6.3 使用最小 guest 用户空间、Ubuntu 6.8 内核和 USB/LVM/ext4 根盘，**不使用完整 Ubuntu 用户空间**。

运行：`20260925-005333-probe-stall`。

- 注入：QMP 将 SCSI 盘后端吞吐限制为 1 byte/s；节点和 USB 设备不移除。
- 配置：Guard 窗口 4 秒，内核无路径窗口 6 秒。
- 结果：延迟持续约 **12.244 秒**；早/晚观测间被测追加+fsync 操作无新增完成记录，DM 路径仍 A，Guard 仍 ready、0 次恢复；RAM shell 可用。
- 解除限速后原写入进程继续，未记录应用错误，最长单次写入约 **12.210 秒**。
- **结论：无路径超时不是端到端 I/O 上限，DM A 不是已验证完成进展。**
- 边界：这是 QEMU 后端延迟代理，不是精准复现某款 UAS 桥接固件死锁；未触发真实硬件 EH 的全部分支。

### 6.3 新实验 E-SUSPENDED：暂停后管理器死亡

运行：`20260925-005334-probe-suspend`。

- 注入：STOP 管理器，删除虚拟 USB，等 DM 报路径 F；在 RAM 中执行与恢复流程相同的 noflush/nolockfs suspend，随后 KILL 管理器。
- 配置：同上 4/6 秒。
- 结果：等待 9 秒后映射仍明确报告 **Suspended**，观测间被测追加+fsync 操作无新增完成记录，RAM shell 可用。
- **结论：内核无路径超时不负责恢复 DM core 暂停；必须补控制事务崩溃收尾。**
- 边界：构造的是管理器死亡后的相同状态，不是随机击中 Guard 两条系统调用之间；没有宣称发生了数据损坏。

这两项的 `passed=true` 表示“预期边界被成功观察”，**不是恢复成功**。完整记录见 [experiments.json](experiments.json)。复现前须按 [lab/README](../../lab/README.md) 准备依赖、匹配内核并运行 `lab/build.py` 生成 `lab/work/build.json` 和 initramfs；干净检出不自带镜像。随后运行：

```bash
python3 lab/research_probe.py slow-backend
python3 lab/research_probe.py suspended-manager-death
```

### 6.4 新实验 E-UPSTREAM：标准 multipathd 的能力与准入边界

独立最小 RAM 根环境运行发行版原装 `multipathd` 和 `udevd`；使用 UAS 整盘 → multipath → kpartx 分区 → LVM → ext4 **数据卷**，没有运行 Guard。这是标准组件可行性对照，**不构成完整 Ubuntu 根盘迁移验证**。配置启用 USB、strict 登记 WWID、`recheck_wwid yes`、`no_path_retry 8`；完整配置和命令见 [复现脚本](multipathd_probe.py)。

这里采用默认 request-based multipath，表中没有 Guard 基线的 `queue_mode bio`；请求完成、暂停与退出语义必须按选定模式分别验证。探针没有配置 Guard 所用的 `queue_if_no_path_timeout_secs`，`no_path_retry 8` 是用户态路径检查策略，**不是 8 秒内核兜底**；本轮没有测试 stock daemon 在等待/切换时死亡后的行为。

| 运行 | 注入与调度 | 结果 |
|---|---|---|
| `20260925-005100` | 同端口三次移除/接回；默认权限 | 最后快照 231 次 fsync 成功、0 错误；最大单次写等待 0.512 s；最终 233 条在线前缀回读一致；主线程 SCHED_RR/99 |
| `20260925-005151` | 同样三次；移除 CAP_SYS_NICE | 230 次 fsync 成功、0 错误；最大 0.534 s；最终 231 条回读一致；主线程 SCHED_OTHER/0 |
| `20260925-005341` | 普通调度；换成独立空白盘，保持容量、USB serial 和 SCSI WWID | 被重新接入活动映射；快照仍显示 142 次 fsync 成功、0 错误；最终 143 条已确认前缀回读不一致；替代盘文件中找到 46 条真实负载记录 |

第三组很重要：替代 `wrong.raw` 通过独占新建再 truncate 构造为 1 GiB 稀疏空白文件；原始样本没有保存注入前整盘哈希或分配量字段，不能宣称有这些测量。VM 退出后只读检查，在偏移 `153620480` 至 `153804800` 找到编号 97–142 的 4 KiB 记录，实际分配量为 `1,318,912` 字节；原盘保留 0–96，双方对应的另一组位置均为零。替代盘没有原分区/PV/文件系统内容，但旧的上层映射继续指向稳定 multipath，新的写入落到了这个错误后端。QMP blockstats 的请求计数字段为零，最高写偏移却从 0 增至 `153808896`；直接文件内容与 daemon 接入日志是主要证据。

**结论是 WWID 信任合同与本项目额外准入合同不等价，不是证明 multipathd 违反了自身设计。** 测试刻意复制呈现给主机的标识，未证明某款真实桥接会如此，也不代表密码学攻击模型。PV/VG/布局核验可以拒绝这一空白盘，仍不能识别所有完整克隆或已被外部修改的原盘。自定义 checker 的放行竞态尚未单独实测，不能用本组替代该证明。

资源观测：两组正样本 daemon 各有 7 线程，RSS `27,748 KiB`；10 秒进程 CPU tick 采样约单核 `0.10%`。这不包含 udevd/其他依赖，也没有亚秒峰值数据，不能和 Guard 的 cgroup/100 ms 测量直接排名。`VmLck=420,196 KiB` 是锁定虚拟地址范围的观测，**不是 410 MiB 实际驻留物理内存**；需进一步 PSS/smaps 归因。普通调度可行已得到样本支持，CPU 配额与压力下恢复期限仍待验。

证据和哈希见 [multipathd-results.json](multipathd-results.json)，源代码分析见 [组件研究](upstream-components.md)。写线程在快照后仍继续，所以最终回读条数略有增加；回读采用 `posix_fadvise(DONTNEED)` 后的普通读，未做冷启动，不称为 O_DIRECT 或断电持久性验证。准备基础实验构建及发行版 multipath-tools、kpartx、udev 依赖后可复现：

```bash

python3 research/2026-09-25/multipathd_probe.py --deny-rt
python3 research/2026-09-25/multipathd_probe.py --deny-rt --wrong
```

### 6.5 证据不足与不能外推的结论

- QMP `device_del/add` 保留同一 backing file，不等价于桥接/SSD 真断电及易失缓存丢失。
- 在线前缀回读不等价于冷启动耐久性、全文件一致性或数据库事务正确性。
- 当前块读取验收曾只检查 probe 执行成功，没有完整断言长度和 ext4 magic；journal 检查只匹配一个字符串。应先加强判据再扩大“全通过”的含义。
- 服务 PID、boot ID、根挂载 ID 不变是必要证据，不覆盖所有应用内部状态。
- `--gap 0` 表示不人为额外等待，不表示电气断联或系统恢复为 0 秒。

## 7. 职责划分：消除重复，而不是把一切下沉

| 组件 | 唯一职责 | 明确不负责 |
|---|---|---|
| USB/SCSI 驱动 | 传输、命令生命周期、错误恢复/取消 | 解析 PV/VG，判断应用一致性 |
| dm-multipath 内核 target | 块路径选择、允许重试的路径错误、无路径排队机制 | 发现“原盘”、LVM 布局认证、修复 ext4 |
| 一个用户态路径 owner | 发现实例、调度检查、准入后改变映射、管理恢复事务 | 执行业务重试、并发与另一 owner 改同表 |
| 准入策略模块 | 登记身份、布局与唯一性规则，给出可解释拒绝原因 | 管理第二份独立映射状态机 |
| 最小事务监督者 | 识别 owner 退出，按已验证事务状态接管/降级，维护独立救援入口并验证所覆盖故障下可用 | 重复实现设备发现和路径故障判定 |
| 文件系统/应用 | 自身日志、持久性和业务恢复 | 推测 USB 身份或强行接回底盘 |
| 独立测试/观测 | 记录错误、完成进展、故障时间线、数据正确性 | 用“服务还活着”替代所有验收 |

“监督者”不必是又一个大 daemon；可以复用可靠的启动/服务管理加小型 RAM 接管程序。systemd 本身也依赖存储、内存和可调度性，不能未经实验就当成根失联时绝对可靠的监督域。

后续 7.0 源码核验发现，6.16 引入的 `DM_MPATH_PROBE_PATHS` 已可提供“读取活动路径并将路径错误标坏”的内核后端。现已将其接入 Guard 的恢复确认阶段，替换 resume 后直接 ready 的旧分支；它可能同步阻塞，不能证明身份或全系统健康，不改变上表中的唯一管理者与准入职责。来源见 [版本对照第 9 节](VERSION-STUDY.md#9-实机更新后新增可用的路径探测接口)，接入约束与新的实测覆盖见 [接入记录](../../lab/KERNEL-PROBE.md)。

## 8. 技术路线比较与决策门槛

后续版本对照已确认：0.15 可以在 Noble 库环境私有构建运行，无需混装另一发行版；Linux 7.0 已通过现有 Guard 的完整 Ubuntu/Git 三次拔插，但在途停滞和暂停死亡边界仍在。下表 B/C 应使用经过同口径验证的新版基线，避免重新实现已有优化。[版本证据](VERSION-STUDY.md)

| 路线 | 复用程度 | 优点 | 主要风险/代价 | 决策 |
|---|---|---|---|---|
| A. 收敛现有 Guard + upstream DM | DM/LVM/工具复用，自有小状态机 | 已有根盘实验；严格准入易审计；低健康 CPU | 生命周期、事务与版本适配由我们维护 | 当前研究基线，先修 P0 |
| B. stock multipathd + 配置 | 最高 | 成熟发现、path checker、路径管理、日志；单盘重接已实测可用 | 同 WWID 空白盘被接入；根盘集成、期限与资源仍待验 | 作为标准对照；本轮配置未满足严格准入 |
| C. multipathd 的有限用户态扩展 | 高 | 通用能力复用，额外策略可集中 | 需覆盖 create/add/reload/reinstate 所有放行点；维护小补丁 | 优先做最小准入扩展验证，再与 A 同口径选型 |
| D. 用 C/Rust 重写小管理器 | 仍复用内核与库 | 可减少解释器/工具驻留，精确资源控制 | 重写不自动修正确性，FFI/ABI/打包有成本 | 明确合同、稳定实验后再做 |
| E. 新增/扩展内核 DM target | 低到中 | 仅适合现有内核机制确实无法表达的通用能力 | 内核崩溃风险、ABI/升级/签名、测试面大 | 当前不推荐 |
| F. eBPF 监测层 | 观测复用 | 研究在途请求、延迟和完成历史 | 不能通用安全重接根盘；额外内核依赖和开销 | 仅按需诊断，不当恢复核心 |

stock multipathd 的几点关键约束：

- 本机 0.9.4 有 `allow_usb_devices`，默认排除 USB；登记 WWID 配合 strict find_multipaths 可支持已登记的单路径设备，不能以默认行为推断支持程度。[U1]
- 标准发现面向整盘 `DEVTYPE=disk`；当前直接以分区为 multipath 后端的布局不能假定可直接接管。[U1]
- `recheck_wwid` 并不等于 USB+PV/VG/LV 全核验；源码中的 fresh VPD 读取失败也不能解释成强制拒绝所有新路径。[U1]
- 自定义 path checker 返回 DOWN，并不能未经审计就证明该路径从未进入可接收 I/O 的活动表。create/load 与后续状态同步之间的关系必须逐条追踪。[组件研究](upstream-components.md)
- 0.9.4 daemon 有 realtime 调度和锁内存行为；本轮实测默认主线程 RR/99，拒绝 CAP_SYS_NICE 后 OTHER/0，后者仍完成三次重接。**不能把我们普通 Guard 的 CFS CPUQuota 结论直接套给默认 multipathd**。部署前仍须核对全部线程、依赖内存与压力下服务限制。[U1][E4]
- `lvmdevices` 是身份和允许列表工具，不是负责在途 I/O 恢复的 daemon；它不能替代路径 owner。[U2]

最终选择 B/C/A 的门槛是：同一故障矩阵、同一准入合同、同一上层 I/O 验收和同一资源口径。不能仅凭“更成熟”或“代码更少”选择一个未达到合同的实现。

### 8.1 如果目标是整机连续性，必须比较存储布局方案

当前单盘单路径设计没有另一份在线数据源。它能争取“等待后继续”，不能在盘长期不可读时凭空提供未缓存的数据。若实际优先级是工作环境少中断，应同时比较以下路线，而非只在 daemon 之间选择：

| 结构方案 | 能解决什么 | 主要代价与边界 |
|---|---|---|
| OS 根目录、swap、恢复日志放可靠内置存储，USB 保留工作数据 | USB 丢失不再直接切断系统工具与换页；管理器可更简单 | 涉及数据迁移/启动配置；USB 上工作进程仍可能阻塞；本机内置盘现有用途不能擅自覆盖 |
| 两份数据、真正独立故障域的镜像 | 单一路径/设备失效时有另一份数据可读 | 增加设备、容量及写入；重建、一致性和共同电源/Hub 故障仍需处理；不是只开 multipath 就获得镜像 |
| 整个只读系统驻 RAM、可写层独立设计 | 系统代码不依赖故障根盘 | RAM 成本明显增加；可写数据持久性另解；不能把当前小型救援 tmpfs 当完整 RAM OS |
| 内置持久缓存/日志加 USB 后端 | 部分负载可延后访问后端 | 未缓存读取仍依赖后端；writeback 引入脏缓存、恢复和一致性责任，不是最小方案 |
| 当前 USB 根盘 + 有界排队重接 | 保留可移动系统布局，改动范围较集中 | 只能有条件连续；须接受长断联/驱动故障时降级 |

以上是不同产品取舍，不能默认为用户批准迁移。可靠线材/供电、合适桥接、减少共同故障域也应与软件并行评估；不能用 DM 掩盖反复发生的硬件问题。关于镜像、缓存、overlay 的基础语义参见 [Linux MD](https://www.kernel.org/doc/html/v6.8/admin-guide/md.html)、[DM cache](https://www.kernel.org/doc/html/v6.8/admin-guide/device-mapper/cache.html)、[OverlayFS](https://www.kernel.org/doc/html/v6.8/filesystems/overlayfs.html)。本轮没有实施这些替代布局。

## 9. 建议的判定模型与状态合同

不要用一个 `healthy` 布尔值混合四种事实。对外状态至少分开：

1. **实例身份**：旧实例仍在／新实例出现／候选模糊／已核验。
2. **传输与完成进展**：有进展／无请求／可疑停滞／明确路径失败。
3. **控制事务**：正常／候选验证／inactive 已加载／已暂停／已恢复／接管中。
4. **上层错误历史**：未观测到／已观测到错误／观测不完整。最后一项不能伪装为“确认无错”。

建议状态机：

```text
正常监视 → 可疑观察 → 明确失效、开始有界等待
                            ↓
                    唯一候选就绪与完整准入
                            ↓
                 加载候选 / 最终实例复核 / 切换
                            ↓
                  路径可用 → 上层验收与业务继续

任何阶段：超时、身份不明确、控制事务丢失、错误历史不清
    → 停止新的自动接入决定，保留诊断和有定义的接管流程
```

当前 Guard 的正常监视可保持事件等待和低频纯内存状态检查。无完成进展仅触发观察，不直接授权切换，不无条件主动扫描磁盘。若采用 multipathd，它现有的 TUR checker 会发送真实 SG_IO 设备命令，即使不传输数据，也不属于纯内存检查；本轮配置为 1–4 秒轮询。应把主动检查的频率、USB 唤醒和 CPU 成本纳入选型，再决定是否保留或调整。主动 checker 也可能阻塞，数据读探针则只覆盖有限 LBA，都不是无成本万能信号。

对于候选验证，定义一个带期限的实例凭证：登记身份、diskseq/设备号/容量/块大小、分区/PV/VG/布局版本、验证时间与 owner epoch。实际提交前再检查，检测到变化则作废。它减少 TOCTOU 风险，但最终绑定证明仍需要内核接口和实验支持。合法的 LV 扩容、布局或分区调整必须经过受控重新登记：先协调唯一 owner，再验证新配置和实际映射，最后更新版本；不能在断联恢复中自动把任意新布局当成已批准变化。

## 10. 恢复事务和退出策略

P0 要求是：对所有有副作用的阶段，知道失败后处于何种状态，并有唯一接管者。

- 在 RAM 保存有界事务记录，包含稳定 map UUID、当前/候选身份、阶段、期限、active/inactive 表摘要。记录必须在对应副作用前后有清晰顺序；仅写一个“ready”字符串不够。
- 每个 map 只有一个 owner，接管前确认旧 owner 已退出或已被隔离；用锁、epoch 和实例检查避免两个进程同时恢复。
- 审计是否可以利用 DM resume ioctl 内部的 suspend/swap/resume 收窄用户态崩溃窗口；本轮已采用单次 resume 并做用户态阶段死亡测试，仍不是任意错误下的原子事务或自动回滚保证。[K6]
- 在 create/load/suspend/resume 每一阶段注入 SIGKILL、超时和设备再次消失，验证 active/inactive 表、请求归属和接管结果。
- 超时预算分开表示：驱动/EH、无路径排队、候选验证、切换、监督接管。给用户的是有证据的行为范围，不把多个不同起点的定时器统称“10 秒一定恢复/失败”。
- 不在状态不明时自动 fsck、强行 remount-rw 或 reset 整个 USB 控制器。reset 可能影响 Hub 下其他设备和旧请求完成语义。
- 明确区分“停止自动接回”与“所有写入已被安全栅栏”。当前只能证明前者的部分场景。

## 11. 资源预算与性能策略

### 11.1 测量全账

```text
额外 RAM = 相对同负载、无保护基线的系统内存增量
归因项：管理器、RAM 工具/动态库、监督/日志、内核请求、脏页/待写数据
共享页、tmpfs 被映射页、BIO 引用的脏页必须去重，不能直接相加
```

256 MiB tmpfs 是容量上限，不是当前实际使用量；RSS 不等于独占内存；共享库可能重复计入多个进程 RSS。应报告 PSS、cgroup memory.current、tmpfs 使用、锁页/不可换出量、内核队列和断联期间增量，避免混用。不得把父进程 `14.63 MiB` 称为整个救援系统的开销。

队列/脏页需求取决于负载和等待时间。`写入速率 × 失联时长` 只能作粗略压力估算，不能当作 DM 必定分配这些内存的公式；背压、缓存和阻塞会改变行为。必须测内存压力时原应用与救援的可调度性。

### 11.2 当前可保留的低开销设计

- 当前 Guard 的健康监视保持常驻库查询、阻塞事件、1 秒复核，无高频创建子进程。multipathd 候选还要计入 TUR 轮询的真实设备访问，不能宣称拥有相同的纯内存监视成本。
- 事件合并、单个恢复流程、指数退避与针对登记设备的核验继续保留。
- 日志必须有界；原 append-only Guard 日志已在本轮替换为双文件轮转，事务/状态记录也限制大小，实验 agent 的独立原始采集按运行目录保存。
- 映射切换阶段的少量命令开销优先服从正确性；若迁移到库调用，应保留完全相同的 flags、错误处理和观测顺序。
- 20%/20 ms 配额目前是当前普通调度 Guard 的已测可行点，不是最优点；不能限制所有内核 worker 或恢复后的应用峰值。
- 对救援关键代码/栈/依赖建立明确不可换出策略；禁止它依赖故障盘上的 swap。不要未经测量直接关闭整个系统 swap 或无限 mlock 全部工具。
- C/Rust 替换 Python 的收益应在全账中测量；如果主要成本是工具 tmpfs 和队列，先换语言未必是最大收益。

建议工程目标（**尚非保证**）：健康监视平均 < 单核 0.5%，100 ms 窗口 P99 < 5%；事件洪泛不误恢复且有限 CPU；正常与失联阶段的全部 RAM 上限按最低目标机器可用内存确定。每个目标都要记录基线、硬件、样本长度和失败条件。

## 12. 下一阶段验收矩阵

| 优先级 | 要回答的问题 | 注入/负载 | 必须观察的结果 |
|---|---|---|---|
| P0 | 管理器在每个事务阶段死掉怎么办 | create/load/suspend/resume 前后 SIGKILL | 唯一接管、无永久暂停、无错盘 I/O、错误语义明确 |
| P0 | 下层永不完成如何退出 | blkdebug 挂起、受控 SCSI/UAS 超时 | 定位阶段；没有双重提交/无限遗留 worker；救援可用 |
| P0 | 内核先超时、控制层后接回 | deadline 边界抖动/CPU 节流/长核验 | 不把错误已上报的状态宣称完全恢复 |
| P0 | 候选实例在最后一刻变化 | 同名/同 dev_t 条件、验证中拔盘、重复标识 | 每次拒绝或绑定到已验证实例，未准入路径不承接上层业务 I/O；允许受控只读核验 |
| P0 | 已同步数据是否真耐久 | 数据+目录 fsync、独立确认日志、冷启动回读 | 已确认序列、内容与顺序一致；故障后不能靠缓存掩盖 |
| P1 | 所有请求类别是否符合语义 | buffered/direct read/write、flush/FUA、discard、mmap | 不只验证普通追加写；取消/错误结果正确 |
| P1 | 内存/日志是否有界 | 多应用高写入、低内存、长等待、事件风暴 | 监督和救援不依赖同盘换页；无无界 RAM 增长 |
| P1 | multipathd 能否替代 | 整盘标准布局，UAS/BOT，同样矩阵 | 准入、错误历史、资源、事务至少达到基线 |
| P1 | 新内核路径探针能否减少自写逻辑 | `DM_MPATH_PROBE_PATHS`；拔插、停滞、暂停竞争、多路径组与非路径错误 | 确认实际读取/标坏范围，成功返回不误报健康；最多一个未完成调用，无无界 worker |
| P1 | 启动/升级能否可靠 | initramfs、root PV 单路径可用、裸路径排除 | 不重复激活；回滚可启动；没有第二 owner |
| P2 | 实际硬件是否符合模型 | 可控 USB 电源/线缆/Hub/端口、PM、热条件 | 单变量实验；独立日志；真实 flush 与错误类别 |
| P2 | 业务如何恢复 | Git、数据库 WAL、桌面会话、网络超时 | 逐应用定义成功；不以 PID 存活替代事务正确 |

测试必须有不注入故障的同负载基线和预期失败样本。注入错误或破坏数据只能作用于可丢弃 VM/测试盘。真实根盘试验必须在离线备份、可启动回滚和独立日志已就绪后开展；本轮未执行。

## 13. 实施顺序与退出条件

**阶段 A：纠正合同和验收。** 明确 F01–F30 范围、补充错误历史与实际块读取判据、记录所有 phase 和队列进展。退出条件是同一结果不再同时被解释为“恢复成功”和“预期超时”。

**阶段 B：收敛控制事务。** 消除/接管暂停死亡窗口，验证设备实例绑定、超时竞争、工作单元生命周期和有限日志。退出条件是 P0 在固定故障点和随机调度下均通过；不能只重复已有快拔样本。

**阶段 C：标准组件扩展对照（与 A/B 并行）。** 已完成 stock 标准整盘初步对照及 0.15 新版验证；本轮补充新版晚归终止实验和全部放行入口审计，发现正确扩展还需多处生命周期/终止/CLI 集成，因此按成本退出条件暂停分叉，保留单一 Guard；详见 [准入选型](MULTIPATH-ADMISSION-DECISION.md)。若未来重启此路线，仍须验证扩展及完整 Ubuntu 根盘场景。现有 Guard 在新内核上的根盘成功不等于 multipathd 根盘集成已通过。退出条件是职责不重叠、附加策略在放行前生效、资源口径可比较。若改动面或总成本过大，则保留并收敛 A，不为复用强行维护复杂分支。

**阶段 D：资源与启动集成。** 再决定是否重写小管理器，压缩工具依赖，建立 RAM 驻留/监督、全磁盘故障域和 initramfs 回滚。退出条件是内存压力及升级回滚实验通过。

**阶段 E：硬件验证。** 将 USB 电气/桥接缓存/PM 等 QEMU 不能等价模拟的部分放到独立测试硬件，不使用真实工作根盘作为首个试验品。

只有当 A–D 显示明确机制缺口，才建立内核补丁路线：最小复现、失败语义、上游接口设计、固定版本实现、fault injection、自测/回归和回退方案。不能仅以“把功能都放在 DM 看起来更统一”作为进入内核的理由。
