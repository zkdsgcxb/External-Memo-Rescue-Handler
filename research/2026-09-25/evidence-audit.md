## 1. 当前可以相信的结论

1. 当前实验确实从故障 USB 后端上的 **ext4 → LVM LV → 单路径 BIO dm-multipath → USB 分区** 启动根目录，不是健康根系统另挂一块故障数据盘。建图先于 PV/LV 创建与根挂载：[agent.py](../../lab/guest/agent.py)，34–103 行；根切换：[init.sh](../../lab/guest/init.sh)，36–40 行。
2. 预置保护层在已测 QMP 移除/重建场景中，可以保持上层 LV、挂载、受观测进程与服务实例，追加写入/fsync 零错误，Git 克隆最终完整性检查通过。成功是“原进程在短暂停顿后继续”，不是自动复活已退出进程。
3. 手动刷新仅能修正映射；此前无保护的持续写入组确实出现 journal abort 与应用错误，后来块读取恢复也不等于文件系统恢复。[原实验验收](../../lab/VALIDATION.md)。
4. 当前事件监视已显著降低健康状态 Guard 的 CPU 开销，但没有测量保护层的全系统数据路径成本、故障期间总内存峰值或长期泄漏。
5. 超时与错误盘样本的 `passed=true` 表示拒绝/释放等待符合预期，同时产生应用错误；不能和正向“系统无错误继续运行”混算。

最初实机事故仍然是待解释的事故。现场没有捕捉到末尾 USB disconnect、UAS reset 或块层错误，不能从 QEMU 能复现某条故障链推出实机事故唯一根因已经确定。[现场记录](../../ram-rescue-demo/incidents/2026-09-23-near-1100/README.md)，5、11、17–19 行。

## 3. 验收项实际检查了什么

| 验收项 | 当前实现 | 保证边界与需补的检查 |
|---|---|---|
| 应用没有 I/O 错误 | 每次打开同一文件，以追加方式写序号和 4 KiB，再 fsync；在 RAM 记录成功/失败 | 单线程、较低并发、固定大小；不代表 mmap、direct I/O、异步 I/O、数据库或大批量回写 |
| 已确认数据存在 | 将 RAM 中所有成功记录重建为预期前缀，在线读取工作文件比较 | 支持这些已确认记录的在线可见完整性；未断电/冷启动，不能独立证明 NAND 持久性或设备缓存协议实现 |
| 绕过文件缓存读块 | `O_DIRECT` 读取根 LV 开头 4 KiB，并记录 ext4 magic | runner 只检查动作没有抛异常，未断言 `bytes == 4096` 和 `magic == 53ef`，应加强验收 |
| 根文件可读 | 清理干净页/目录缓存后读取 sentinel | 实际走恢复映射的证据更强，但不是全盘内容校验 |
| 根文件系统可写 | 新建/覆盖一个文件并 fsync | 可识别“挂载仍显示 rw 但写入 EIO”；不是完整文件系统一致性检查 |
| 无 journal abort | 搜索最终 dmesg 中是否没有字面串 `Aborting journal` | 未全面检查 ext4/JBD2/块错误，也未验证环形日志是否覆盖丢失；不等价于所有文件系统错误均不存在 |
| 进程存活 | PID + `/proc/PID/stat` 启动 tick、未退出 | 证明指定进程实例仍在；不证明所有线程/会话可用或应用内部状态未受影响 |
| Ubuntu 服务存活 | systemd/journald/D-Bus/三个实验服务及写负载的状态、PID、启动 tick、重启计数相等 | 不含 GNOME、SSH/TLS/网络会话、数据库、所有系统服务 |
| 原挂载和上层映射 | 自动验收比较 LV 节点/依赖；快速组另保存挂载行与 DM 表 | 需要将 mount ID/UUID/table equality 统一纳入机器验收，不能只依赖人工解释 |
| Git 完整性 | HEAD、`git fsck --full`、干净工作树 | 覆盖固定版本 shallow clone 的对象与检出；不是全历史或任意应用一致性 |
| RAM 救援可用 | 心跳与独立 root shell 探针 | 健康内核、足够内存条件下有证据；不是 OOM、全局死锁、控制器锁死中的存活保证 |

源码位置：[workload.py](../../lab/guest/workload.py)，7–22 行；[agent.py](../../lab/guest/agent.py)，232–270 行；[auto_run.py](../../lab/auto_run.py)，245–275 行；[ubuntu.py](../../lab/guest/ubuntu.py)，79–98、123–133 行。

细节：runner 在 `probe` 中执行过 drop_caches，然后做写探针和前缀回读，因此比纯缓存回读更有说服力；但持续写负载并未停止，脏页不会被 drop_caches 强制清除，前缀读取本身仍是缓冲 I/O。应把当前结果称为“在线数据完整性检查”，不称“断电持久性验证”。

## 4. 尚未覆盖的重要故障轴

### 4.1 故障注入的物理含义

当前 host 用 QMP `device_del`，收到 `DEVICE_DELETED` 后再 `device_add` 原 backend；其底层 raw 文件一直存在，同一个 QEMU 进程持续运行。[auto_run.py](../../lab/auto_run.py)，167–208 行；[run.py](../../lab/run.py)，101–128 行。

它覆盖的是虚拟 USB 设备模型的移除/重建、guest 枚举、路径替换。它**没有主动模拟** SSD 断电丢失易失缓存、桥接固件停滞、协议违规完成、NAND 错误、Hub 供电下降、LPM/睡眠问题。QMP 删除确认与 guest 旧 gendisk 最终释放、全部旧请求完成也不是同一个事件。不能将 QMP 约 0.1 s 的控制耗时当成物理断联时间或 guest 完成恢复时间。

### 4.2 请求语义

缺少同时存在未完成读、写、flush/FUA、discard、写零、mmap 页故障的随机相位注入。没有确认旧请求从提交到最终完成只发生一次、没有遗失/重复完成、数据顺序符合要求。当前追加小文件 fsync 很有价值，但不足以代表任意深队列或多线程重叠写。

优先增加的独立验收：分块随机数据与校验和、提交/完成请求关联、多个线程的明确持久化边界、恢复后冷启动重读、在停止并卸载的克隆镜像上离线 `e2fsck -fn`。文件系统检查不是应用事务正确性的替代品。

### 4.3 实例与身份

当前登记检查 USB VID/PID/serial、整盘扇区数、分区号/PARTUUID、PV/VG UUID/name，并比较 LV 段布局；只有一个候选才继续。[rescue.py](../../ram-rescue-demo/src/rescue.py)，46–98 行；[path_guard.py](../../lab/guest/path_guard.py)，39–49、105–118 行。

尚缺独立 VM 覆盖：两个完全克隆的相同 UUID/PV 同时出现；USB 序列号空值/不稳定/多 LUN；盘名与 sysfs 路径全部复用；相同标识下逻辑扇区大小/分区起点改变；最后校验到切换间再次拔盘；核验期间 LVM 元数据改变。

当前使用 fd pin、`st_rdev` 与 sysfs 字符串重检，可以减少竞态，但未使用磁盘实例代次标识；不能写成“彻底消除 ABA/设备复用竞态”。当前布局归一化会去掉 `seg_pe_ranges` 中设备名，适合已限定单 PV 的实验，不应直接扩展为任意多 PV/LVM 类型的完整核验。

### 4.4 控制器失效及期限

现有 kill-manager 只在已经移除设备、获得 waiting 观察后杀进程。[auto_run.py](../../lab/auto_run.py)，193–201 行。没有在 inactive table load、suspend、resume 各阶段杀死或挂起管理器，也没有模拟 DM ioctl 卡住、libdevmapper 错误、事件队列溢出与服务自动重启后恢复状态。

Guard 到期后终态拒绝自动重接，是明确的策略；但不能将 `queue_seconds` 宣称为每个请求端到端延迟的硬上限。查盘命令、内核驱动在途请求、DM table swap 都可能先消耗时间；用户态 subprocess timeout 不证明不可中断内核等待一定被及时取消。当前 deadline 在切换前检查，`load → suspend → resume` 之间仍有执行间隔；应针对“内核已放出 EIO，但用户态随后宣布 ready”建立独立观测和故障测试。[path_guard.py](../../lab/guest/path_guard.py)，74–80、108–145 行。

### 4.5 系统拓扑与启动

当前只支持单 USB 盘、DOS 单分区、单 PV、两个线性 LV、ext4。没有覆盖 GPT 多分区、整盘 PV、标准 whole-disk multipath + 分区映射、LUKS、thin/cache/RAID/snapshot、swap 位于故障盘、多 PV VG 或多设备并行故障。

Ubuntu 是官方 Server rootfs + 自制 initramfs 直接 switch_root 到 systemd；没有测试 GRUB、Ubuntu 常规 initramfs、启动期间断盘、内核升级后 RAM 工具/模块兼容性、休眠恢复、桌面环境。实验屏蔽 multipathd 与部分 LVM 自动管理服务，证明的是单一 owner 条件，不证明与默认 Ubuntu 管理栈无冲突。[ubuntu.py](../../lab/guest/ubuntu.py)，29–35 行。

### 4.6 统计稳定性

每个场景是少量样本，连续重接最多几个周期；没有随机种子与重复次数、分位延迟、泄漏斜率、长期事件风暴、CPU/内存压力下的成功率。不同 VM 并行与单 VM 的 Git 总耗时不可直接相减作为保护层成本。[Ubuntu 验收说明](../../lab/UBUNTU.md) 已正确注明此点，应保留。

## 5. 资源开销应该怎样记账

已有 CPU 数值可信地描述了一个有限范围：Guard cgroup（包括子进程）的 CPU 时间；采样器和事件产生器在别的 cgroup，不包括内核异步 worker 或应用。[measure_guard.py](../../lab/measure_guard.py)，11–37、85–86 行。

| 样本 | 单核平均 CPU | 约 100 ms 窗口最大值 | P95 |
|---|---:|---:|---:|
| 健康约 30.2 s | 0.1043% | 1.5123% | 0.9983% |
| 约每秒 100 条合成 change，约 10.2 s | 0.8891% | 2.1808% | 1.3735% |

CPUQuota=20%、周期 20 ms，对应 `cpu.max=4000 20000`。采样区间内 `nr_throttled` 没有增长；启动前累计已有两次节流。不是“系统永不节流”，也不是任意微小时刻 CPU 使用率永不超过 20%。

常驻父进程 RSS=15,335,424 bytes，约 **14.63 MiB**。这个数不等于解决方案内存成本，至少还包括：

| 成本 | 当前事实 | 正式测量建议 |
|---|---|---|
| 工具 tmpfs | guest `/run/rescue` 上限 256 MiB、noswap；整个运行库目录复制进去 | `df`/statfs 实占、tmpfs shmem；文件总量只是预估，不能当 RSS |
| Python 与共享库 | Guard RSS 已测；agent、shell、日志、child 另有占用 | 每进程 PSS/RSS、cgroup `memory.current/peak/stat`，避免共享页重复计算 |
| 排队 I/O 与脏页 | 未采集；来自内核和应用，未必记在 Guard cgroup | 总系统 memory/PSI、dirty/writeback、slab、bio/request 数与排队字节 |
| 日志 | Guard `path-events.jsonl` 持续追加，当前没有轮转；实验 workload 日志也一直增大 | 有界环形日志、丢弃计数、长期故障循环测增长率 |
| 冷启动额外成本 | initramfs 复制/解包与模块加载，未提供启动峰值 | 启动耗时、解包峰值、释放后的稳定占用 |
| 数据路径性能 | 没有 DM 直连对照吞吐/延迟测试 | 同一镜像、相同缓存/并发/CPU条件，对照 direct-LVM 与 mpath-LVM |

当前 lab/work/rootfs 全部普通文件逻辑大小为 87,212,429 bytes（约 83.17 MiB），仅是本次查看的构建树文件体积；不能当作实际驻留量或给生产的内存承诺。构建包含 Python 标准库、工具、模块等，[build.py](../../lab/build.py)，36–61 行。未来瘦身应根据可验证依赖清单裁剪，而非只比较可执行文件大小。

生产手动救援包与实验 Guard 不应混为一组资源数。历史生产包文件体积约 54.97 MiB；历史 slice `MemoryCurrent` 约 89.8 MiB；slice 上限 768 MiB、swap=0、MemoryMin=64 MiB。它们属于另一构建及历史时刻，未在本次重新测量。[生产验证](../../ram-rescue-demo/VALIDATION.md)，7、30、48–50 行；[slice 配置](../../ram-rescue-demo/src/ramrescue.slice)。

实验的 tmpfs noswap 保护文件页，不是自动保证所有匿名页与整个控制面都不会被 OOM 或 swap 影响；Ubuntu lab guard 服务目前只设置 CPU 配额，没有对应 memory/swap 参数。[ubuntu.py](../../lab/guest/ubuntu.py)，43–47 行。在真实根盘故障下，应把必要进程、其匿名页、工具文件和依赖服务一起纳入 RAM 可用性合同；先测量，再设置合理的内存保护与边界。

降低日常干扰的下一步应先收窄事件过滤与界定预算，而不是无证据重写语言。当前接收所有 kernel `SUBSYSTEM=block` 消息，10 Hz 合并后查询所管 map；不是仅订阅登记磁盘事件。[dm_monitor.py](../../lab/guest/dm_monitor.py)，45–88 行。事件风暴测试仅生成受管 dm-0 的 change，仍需测非目标磁盘大量事件、非 block 事件、缓冲溢出、丢事件后的 1 s 兜底。

## 6. 建议报告采用的责任合同

目标是每项状态只有一个权威 owner，不是不断叠加监视器。

| 部分 | 应拥有的职责 | 不应拥有的职责 |
|---|---|---|
| Linux USB/SCSI 驱动 | 传输、命令完成、协议恢复/中止、设备生命周期 | 解析 LVM 布局或应用事务 |
| 内核 DM multipath | 稳定块设备、适用请求排队/重试、路径和表的内核并发正确性 | 判断“新盘满足本项目登记策略”、修复文件系统 |
| 单一路径管理器 | 候选发现、路径健康、经过准入后驱动 DM 更新；可评估 multipathd | 与第二个 manager 同时修改同一张 DM 表 |
| 准入/登记策略 | 明确支持拓扑；只读验证预期身份、容量/几何/布局；拒绝歧义 | 自己实现第二套 LVM 元数据解析器、复制每个 I/O |
| 生命周期与资源 supervisor | RAM 依赖、启动顺序、资源预算、失败终态、控制进程重启协议 | 因服务重启就默认故障已恢复、无限重试 |
| 救援与诊断 | 独立入口、故障证据、明确人工处置 | 在已受损挂载上自动 fsck/remount 并宣称透明恢复 |
| 实验验收 | 独立判断真实设备事件、请求结果、同实例与数据一致性 | 只读取 manager 的 ready 日志就算成功 |

身份核验可作为唯一 manager 的准入步骤或适配模块，既不应同时造两个路径管理器，也不必为了“合并模块”把 USB/LVM 格式政策放入内核。是否需要扩展上游 manager，应由 whole-disk/partition 支持、准入前置位置、RAM 驻留与资源测量决定。

对于资源验收，建议把“目标”写成待验证 SLO，不能冒充已经实现的保证。例如：健康单盘 CPU 平均不超过单核 0.2%，100 ms 窗口 P99 不超过 2%，指定非目标事件风暴下 CPU 不超过预算；健康态不得周期性读取媒体；日志内存有上限；验证/恢复只能有一个进行中。每项明确机器配置、窗口、负载、重复次数和失败标准，并保留原始数据。

## 7. 推荐的下一轮实验优先级

1. **先验收安全边界：** 超时与重新连接同时发生、manager 在每个 table swap 阶段被杀、旧请求迟迟未完成。要求无未经准入路径接入、无超时后静默回写、无永久悬挂且 RAM 控制面可用。
2. **再验收数据语义：** 真实 flush/FUA 与强制丢失易失数据模型、随机并发写、校验和、冷启动复核、卸载后文件系统检查。记录哪些已 fsync 的记录必须保留、哪些未确认记录允许存在或不存在。
3. **然后比较工程路线：** 当前分区 BIO 自管方式与标准 whole-disk multipathd 路线，用同一故障/数据矩阵、同一观测器和资源口径比较；不要一边更换拓扑一边放宽验收。
4. **最后做压力与部署集成：** 内存/CPU/事件压力、长时间重复、标准 Ubuntu initramfs/更新/回滚、LVM 限定扫描与唯一 owner，再进入可控硬件试验。

QEMU 可以使时序与后端故障可控，但不能凭虚拟通过证明真实桥接芯片固件、Hub 供电、SSD 断电缓存正确。报告宜把每个故障列为“已验证 / 可在 QEMU 补测 / 需要真实硬件 / 明确不保证”，避免“尽量覆盖全部”变成不可证实的全覆盖承诺。
