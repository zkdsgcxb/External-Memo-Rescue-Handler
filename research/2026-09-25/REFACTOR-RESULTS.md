# 技术路线首轮重构与验收

日期：2026-09-25。当前基线为 Ubuntu `24.04.5`、Linux `7.0.0-34-generic`，不增加旧内核适配。实现及实验在项目工作区中完成，未修改真实 USB 根盘的存储拓扑，也未安装实验 Guard 到宿主。

本轮落实了阶段 A/B 的合同与控制事务、完成阶段 C 选型，并补充阶段 D 的 RAM 启动接管、预算和分项测量。**这些实验通过不等于整份路线的全部 P0、D/E 退出条件完成。** 实际行为、原始报告路径和哈希集中在 [机器可读验收摘要](../../lab/results/2026-09-25-route-refactor.json)。组件职责及复现命令见 [恢复事务](../../lab/TRANSACTIONS.md)。

## 实现变化

1. **拆分准入与控制。** `admission.py` 只处理登记盘只读核验和实例凭证；`path_guard.py` 负责唯一控制者与阶段推进；`guard_state.py` 提供互斥、RAM 记录和分维度观察。原来散在切换函数里的重复核验已替换，未采用的“接管后继续旧候选”接口已删除。
2. **接回前核验更明确。** 持有 fd，核对 diskseq、dev_t、容量、逻辑块大小、分区位置与 PV/VG/LV 布局；期限与 owner epoch 不可沿用到另一事务。inactive 加载后、真正提交前继续复核。当前 active 的 dev_t 若被另一 diskseq 复用，保守拒绝，避免把用户态 fd 当作 DM 对象绑定证明。
3. **缩小暂停死亡窗口。** 删除用户态显式 suspend，再单独 resume 的两步流程，采用内核一次 resume 内部的 suspend/swap/resume。内核仍可能返回部分副作用后的错误；所有 load/resume 命令异常都按实际阶段交接管核对，不能假定命令失败就是“什么都没发生”。
4. **有定义的死亡接管。** flock/epoch 避免重复 owner；DM helper、probe 持有独立锁引用。RAM journal 在副作用前后原子替换。接管只处理已登记的 active/inactive，先 clear inactive 再恢复已知 active 的暂停，停止后续准入；未知状态 blocked。不会把未提交的旧候选直接接入。
5. **低开销与边界表达。** 保留常驻 libdevmapper、事件等待/合并、1 秒兜底、串行指数退避和单个原生 probe。状态区分身份、传输进展、控制阶段和上层错误历史；后者明确 `incomplete`。Guard 日志改为两个各 64 KiB 的轮转文件，journal/state 单文件限 64 KiB。
6. **复用系统监督与内存策略。** Ubuntu 的 Guard 使用 `RootDirectory=/run/rescue` 和 RAM 中的 `ExecStopPost`，不再从失败根卷加载 chroot helper。最小 guest 复用 BusyBox shell 等待并接管。Guard 与后代统一 CPU 20%/20 ms、memory.max 128 MiB、memory.swap.max 0；不把 tmpfs noswap、禁止匿名 swap 与 OOM 存活混为一谈。
7. **验收分清结果。** 正例连续性与预期失败分别记录；probe 零返回不是上层健康证明。负载正确处理短写，完整写入、文件 fsync、目录 fsync 均成功后才 ACK；新增另一台 VM 冷启动回读，避免用原 guest 页缓存证明耐久。

## 当前内核上的实验

下列固定故障和随机死亡试验使用 `v3` 构建；最终业务/冷读使用 `v4`。两个构建只有测试负载 `workload.py` 的短写处理不同，Guard、准入、DM 接口、监督与冷读 guest 的源码哈希完全一致。构建记录中的 `source_commit` 是构建前提交，仅作上下文；实际执行内容以 `source_sha256` 和镜像 SHA256 为准。

| 样本 | 结果 | 验收含义 |
|---|---|---|
| 7 个用户态阶段 SIGKILL | 全部通过 | before/after load、commit 前后、probe 前/启动后、ready 前；清理已登记 inactive，无遗留 DM 暂停，进入 interrupted |
| 未开始恢复时杀 owner | 通过 | 监督关闭无路径排队，不产生新 owner 自动接盘 |
| commit 前到期 | 通过 | 候选没有被提交；接管终态，未报 ready |
| 最终提交前再次拔掉候选 | 通过 | 旧凭证失效，未提交该候选，进入终态 |
| 持续不返回的真实 NBD 请求 | 18 项通过 | 单个 D 态 probe、无第二 owner、flock 保持、RAM 心跳/shell 可用；显式放行后也不报迟到 ready |
| Seed `20260925` 随机时点 SIGKILL，5 组 | 全部通过 | 实际全部落在 verifying；不声称随机覆盖了每个控制阶段 |
| 完整 Ubuntu 的 after_load 死亡 | 通过 | systemd 的 RAM 接管执行、新 epoch、原 owner 退出；此负例未宣称普通根卷服务存活 |
| 相同呈现身份、错误 PV | 通过预期失败合同 | 拒绝接入，6 秒用户态期限附近释放队列；应用出现预期错误，恢复次数 0 |
| 完整 Ubuntu + Git、同端口三次立即重接 | 连续性通过 | 同一 boot/服务/进程；162 次成功写、0 次失败；实际块读取、文件系统可写、Git HEAD/fsck/工作树校验通过 |
| 同 Git 负载不注入故障 | 基线通过 | 180 次成功写、0 次失败，同样通过 Git 与文件系统验收 |
| 两组冷启动 ACK 前缀回读 | 均通过 | 故障组 162 条/664,092 字节，基线 180 条/737,892 字节逐字节一致；原 raw 审计前后哈希不变 |

Git 输入是固定的 Linux 源码浅克隆（83,475 个跟踪文件），其 tag 仅是工作负载输入，不是运行内核。业务正例与无故障基线曾并行运行，最长写延迟分别约 3.718 秒、4.765 秒；这些数字包含宿主争用和 Git 负载，**不能作隔离性能对比或恢复时限承诺**。CPU 资源测量另设独占 VM 窗口。

NBD 最终样本保持请求不返回约 **16.256 秒**。期限前原 owner 主线程处于 S，probe 线程处于 `D / submit_bio_wait`；期限后主线程处于 Z，同一个 D 线程与 flock 仍存在，supervisor 尚未接管。显式释放后收尾为 expired。这证明数量受控、迟到结果不复活准入；**worker 寿命无硬上限，下层永久不完成时接管也不能凭空完成。** 较早的采样按 cmdline 找进程，会漏掉主线程退出后的残留 task；最终摘要采用固定 PID/task 目录观测的补强报告替代该行。

冷读在新的内核和页缓存中进行，允许只在独立 qcow2 overlay 上重放 ext4 日志，原 raw 作为显式只读 backing；核对源报告、实际内核/initramfs 及原镜像前后哈希。它证明这两个虚拟机样本中已 ACK 前缀可见，不能替代物理桥接器断电、flush/FUA 或负例离线数据审计。

## 资源与局部 OOM

最终代码通过 **104 项 lab 单测、14 项原救援单测**。包括真实 fd/flock 继承、probe 阻塞后锁保留、已生效命令异常、凭证失效、有界日志与 ACK 短写判据；并非仅断言实现调用顺序。24 个最终 VM 记录按各自合同通过，原始报告及哈希列于验收摘要。

资源样本单独运行完整 Ubuntu（2 vCPU、3 GiB RAM），100% 表示一颗 guest vCPU；CPU 每约 100 ms 采样：

| 阶段 | 平均 CPU | 窗口 P99 | 观察峰值 |
|---|---:|---:|---:|
| 健康空闲 30.106 秒 | 0.0455% | 0.5673% | 0.6677% |
| 每秒 100 个 DM 事件，10.057 秒 | 0.4958% | 0.9591% | 1.1662% |

两阶段均单线程、无子进程/probe/误恢复，窗口内无新增节流。四个边界快照中，Guard PSS 为 13.454–13.470 MiB、RSS 为 19.375–19.391 MiB，cgroup 记账为 8.965–9.230 MiB；共享 RAM 工具 tmpfs 实用 86.395 MiB。这些视图重叠、归属不同，**不能相加成整体开销**。实际 memory.max 为 128 MiB、swap.max/current/peak 为 0；VmLck 为 0，因为采用 cgroup 禁止换出而不是 mlock。详见[采样口径及原始哈希](../../lab/RESOURCE-MEASUREMENT.md)。没有无保护的全系统内存基线，有限窗口也不能保证任意机器上的瞬时峰值。

独立局部 OOM 实验向 Guard cgroup 加入普通 `oom_score_adj=0` 分配器，尝试触写 200 MiB。内核峰值到达 128 MiB、记录 oom=1/oom_kill=1，杀掉分配器，swap 保持 0；原 Guard 与 epoch 存活。随后 0.2 秒拔插恢复成功，原应用零错误、31 条 ACK 在线前缀一致，直接块读取和 fsync 可写通过。这个样本验证局部预算与一次 victim 选择，**不是全机内存紧张或任意 OOM 受害者组合下的存活证明**；它的 ACK 检查为在线前缀，不与前述两组冷读混用。

## 标准组件选型

[阶段 C 审计](MULTIPATH-ADMISSION-DECISION.md)已覆盖 multipath-tools 0.15 的 create/reload/reinstate 与 CLI/重启入口。新增当前内核实验表明：无路径约 8.076 秒后应用出错，15.401 秒后原盘返回，stock daemon 自动恢复块读取；原 ext4/应用仍只读。这不符合本项目的终态准入合同。

正确扩展需要实例凭证、锁外有界任务、放行入口覆盖和终态生命周期，不能用一个 checker 包装代表完成。因此按路线退出条件，本轮选择继续收敛唯一 Guard，暂停维护 multipathd 准入分叉；没有让两套控制者管理同一映射，也没有新增内核或 eBPF 实现。

## 剩余门槛

- 尚未证明任意内核 ioctl 内部调度点、create/早期启动死亡、所有请求类型、负例 ACK 数据一致性，以及同 dev_t 新实例的最终内核对象绑定。对应情形没有冒充已支持。
- 身份核验的同步工具也可能卡在不可中断 I/O；子进程 timeout 不是取消证明，此时用户态终态记录可能迟于期限。本轮门控专测原生 probe，未穷举每个元数据工具的阻塞点。
- 无路径期限、用户态准入期限、驱动/EH 期限不同；终态不撤销已提交映射或在途写入。已提交后死亡的负例可能继续成功读写，这不违反“停止新增准入”，也不是全写栅栏。
- 状态中的上层错误历史仍为不完整。生产级应用/文件系统观察、策略解锁/重新登记、全局低内存与完整 initramfs 升级回滚尚需专项实现和验收。
- 真正 USB 电气故障、桥接缓存、Hub/PM、物理断电耐久及桌面/数据库业务需独立测试硬件与负载。未把本机工作根盘用作这一步的试验品。

对应下一步应是进一步缩小剩余 P0/P1 风险并完成启动/压力门槛；现有证据支持继续 VM 开发，不支持声称真实 Ubuntu 在任意掉盘条件下完整存活。
