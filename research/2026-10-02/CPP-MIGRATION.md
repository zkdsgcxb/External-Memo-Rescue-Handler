# 完整 C++ 运行时迁移与资源对照

日期：2026-10-02。比较基线：Python `e745e5e4b9cde4ffd21d03f6e45a491ca8400083`。实验平台：完整 Ubuntu 用户空间、同一 Linux 7 内核、QEMU/KVM、USB/UAS 根盘及 ext4/FAT 数据盘。只使用可丢弃镜像；本轮未安装或替换实机 Guard，未做真实拔插。

## 迁移内容

新的 `guard-runtime` 是 C++17 用户空间 ELF，精简文件为约 788 KiB。它完整承担根盘保护启动、健康监视、重新核验原盘、加载/提交 DM 表、内核路径探测、终态处理、死亡接管和登记数据盘的启动。三个保护对象共用同一份控制器代码，每张映射保留各自唯一 owner。

默认 `guard/build.py` 构建 C++ 包；`--runtime python` 显式构建行为对照。C++ ELF、动态加载器、共享库（包括运行时加载的 libdevmapper）和短小 exec 入口都有散列清单，放入救援 RAM 环境。数据盘直接复用该版本；入口执行后成为原生进程，没有新增常驻 shell，也不在活服务下面更新代码。

Python 保留冷态登记/安装、挂载计划生成、手动救援、实验控制及完整参考实现。现有运行时是有明确用途的对照，不会与 C++ 同时争夺同一映射。`dmsetup`、blkid、LVM、systemd/udev 和内核 DM 继续承担原有职责；没有重写块设备或文件系统，也没有增加 eBPF/内核模块。

源码划分和构建命令见 [运行时说明](../../guard/native/README.md)，不变的语义约束见 [迁移约束](CPP-MIGRATION-CONTRACT.md)。

全部六次结果、原始报告 SHA-256、实际 ELF 与运行库散列、极值对应计数窗口及内存快照见 [性能证据 JSON](../../lab/results/2026-10-02-cpp-performance.json)。图片是这些结果的摘要；不将未测时间点补画成不存在的瞬时峰值。

所有 CPU 百分比均以一个逻辑核占满为 100%，合计包含根盘服务与数据盘父 slice（父 slice 已含两块数据盘，不能再加子组），包括恢复期间 blkid/LVM/dmsetup 子进程。采样器、业务负载、udev 和其他内核 worker 不在这个数里。

每次使用新 VM，三段健康场景各约 20 秒：正常、每秒约 100 个无关设备事件、每秒约 100 个相关 DM 事件。恢复阶段采样 16 秒，重连后静默等待 17 秒再访问串口，不用状态轮询干扰恢复窗口。另列 journal 的首次 waiting 到全部 ready 区间，避免用恢复前后的空闲时间稀释恢复 CPU 成本。

“20 ms 峰值”和“100 ms 峰值”是对应名义采样窗口中的平均占用；分母使用实际采样间隔。多个 cgroup 按顺序读取，时刻并非原子一致；本测试内核还可能把中断时间记到被打断的任务。配额不是任意微小时间窗口的硬上限。所有原始极值保留，不将异常高峰删掉后宣布无尖峰。

PSS 是实际物理页的分摊计数，RSS 会重复计算共享页；二者为阶段边界快照。`memory.current`/`memory.peak` 是 cgroup 记账，包含各自被记账的文件页、内核对象等；页的归属会受首次加载者影响。它们不能相互相加，也不能将 cgroup 内存下降全解释成进程私有内存下降。`memory.peak` 和 VmHWM 是生命周期高水位；上表使用连续采样最大值，不把高水位当作该阶段独有的峰值。

## 连续恢复后的内存

单轮同时拔插三盘，共 10 轮；每轮核对原 owner、原业务进程、已打开 FD、原挂载和持久数据。两版各 19/19 项验收通过。

| 三个 Guard 合计 | Python | C++ |
| --- | ---: | ---: |
| 首次恢复前 PSS | 37.863 MiB | 9.572 MiB |
| 首次恢复后 PSS | 38.243 MiB | 10.479 MiB |
| 第十轮后 PSS | 38.491 MiB | 10.656 MiB |
| 第十轮后 RSS | 62.625 MiB | 28.500 MiB |
| 第十轮后 cgroup memory.current | 45.445 MiB | 7.094 MiB |
| 最后五轮 PSS 最大差值 | 0.116 MiB | 0.106 MiB |

第十轮 PSS 下降约 **72.3%**。C++ 第一次恢复时会装入尚未使用的代码与建立缓存，之后仍有约 0.18 MiB 的小幅增长；10 轮内线程和 FD 数保持稳定，没有出现随恢复次数明显累积的资源失控。这不能证明无限运行绝无泄漏。该轮用于功能及稳定内存检查，允许主机其他编译任务同期进行，不把它的 CPU 均值当作正式性能对照。

## 故障验收

- 完整 Ubuntu 挂载验收：Python 和最终 C++ 各 28/28；根盘、ext4、FAT 同时恢复，原挂载、嵌套挂载、bind 子挂载及打开 FD 保留。错误身份被拒绝；原只读策略不被改写；超时后的新挂载被阻止。
- 最终 C++ 事务矩阵：11/11 场景、116 条判据。包括七个阶段的 owner 死亡、没有接管者、截止时间、候选实例再次替换和真实 NBD 下层请求不完成。旧锁未结束时没有第二写入者，没有迟到 ready、残留 inactive 表或永久 suspend。
- 完整 Ubuntu 中在 `after_commit` 杀死 owner：实际 systemd `ExecStopPost` 接管，11/11 判据通过。这补充了最小 RAM guest 的 shell 监督器测试。
- Python 管理、参考实现与测试工具 **355 项**回归检查通过；人工救援另有 **15 项**回归检查通过。
- 原生单元检查：60 项核心、37 项准入、13 项配置/表检查，共 110 项。最终核心 60 项与控制器 13 项通过 ASan/UBSan/泄漏检查，见 [sanitizer 证据](../../lab/results/2026-10-02-cpp-sanitizers.json)；准入模块 37 项也通过独立 sanitizer 检查。规范化 JSON 对 30,601 个有限浮点向量与 Python 逐字比对一致，避免旧 journal/config 摘要在换语言后失配。
- ARM64 与 RISC-V64：完整 ELF 交叉构建并实际执行，每种架构 37+13 项用户态检查及 5 组规范 JSON 对照通过。未把这些结果当作外架构 Linux 内核 USB 恢复验收；见 [架构报告](CPP-ARCHITECTURES.md)。

生产打包集成另做一次完整 Ubuntu 验收，**32/32**：实际调用 `guard.build.payload` 和 `native_payload`，原样使用当前启动脚本、根盘服务及 Manager 模板；没有测试夹具替换控制命令的 drop-in。三个真实 `/proc/PID/exe` 均匹配最终 ELF `72d9d550079b4f73e1954e13f99fa614826758c623eec1d3026aa22bc891b21f`。入口脚本执行后被 ELF 替换，包清单、依赖库和服务文件在前后核验一致。

救援 RAM 包保留了人工救援用 Python，因此整包不会按进程 PSS 的比例缩小。同一登记和基础工具包的普通文件总字节数为：Python **57,752,927 字节（55.08 MiB）**，C++ **61,239,625 字节（58.40 MiB）**，增加 **3,486,698 字节（3.325 MiB）**。新增主要为 806,240 字节 ELF、libstdc++、libgcc；原有共同文件内容相同，自动恢复用的 11 个 Python 模块从默认原生包移除。这是文件负载体积，未包含 tmpfs 元数据/页取整，也不能直接与映射这些文件的进程 PSS 相加或相减。

## 保留的边界

语言迁移减少了控制器开销，未改变硬件、驱动和文件系统的故障边界。DM 可排队的请求由内核等待；已经进入永久下层阻塞的请求不保证被超时取消，磁盘掉电丢失的缓存不能恢复，已经返回到文件系统或应用的 EIO 不能撤销。恢复成功也不证明全部应用历史无错。

本轮实机只读检查中原 Python Guard 仍为 active，根卷、shared、EFI 均保持读写挂载。源码默认已切换到 C++，已安装实机包仍为此前验证版本；QEMU 通过与源码推送不等于实机升级完成。
