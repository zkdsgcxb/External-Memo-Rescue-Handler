# 高权限运行与攻击面评估

日期：2026-10-03。源码基线：`e530cd4bb5fee548aa57ba3a74b2cc137dee3913`。

后续进展：本机首次 C++ 保护启动已核验，见 [启动记录](HOST-CPP-BOOT.md)。本轮已实现启动失败停止策略与救援会话改进，通过候选镜像的 7 项失败启动和 36 项完整 Ubuntu 集成检查，见 [P0 实现与验收](P0-BOOT-AND-RESCUE.md)。以下保留原审阅基线；其中“目前/现有”均指审阅当时状态。自动 Guard 最小权限、安装信任链等后续目标仍未完成，旧版未认证控制台的执行复现也未完成。

**结论：项目没有自建的网络控制服务，输入入口相对集中；但常驻 Guard、介质解析工具和人工救援均具有很高的宿主权限。现有恢复正确性措施不能等同于安全隔离。** 本轮发现应优先核验的未认证启动失败控制台路径；未发现标准部署权限下普通用户可直接利用的命令注入或已证实的远程代码执行路径。这不是安全认证或“没有漏洞”的证明。

## 范围与证据等级

检查了 C++ 事件接收、身份准入、外部命令、配置/事务文件，initramfs 和 systemd 集成，RAM 登录、构建与安装链。读取本机服务有效配置和目录元数据，并核对上游接口文档。没有读取救援密码数据库，没有改变服务、启动项或磁盘映射，也没有进行物理故障、恶意 USB 固件或专门模糊测试。

审阅时本机仍运行原 Python Guard；磁盘上的 C++ 镜像已更新，待重启验收。下文 C++ 实现结论针对源码和候选 ELF，现有服务权限结论来自本机有效配置；没有将两者混为“C++ 已实机运行”。见 [部署记录](HOST-CPP-DEPLOYMENT.md)。

使用三种表述：**已确认实现/配置**、**满足前提即可触及的信任边界**、**尚未证明可利用的风险**。不据此给出 CVSS 或成功攻击概率。

## 威胁模型

| 来源 | 可以接触什么 | 当前判断 |
| --- | --- | --- |
| 仅能访问网络的攻击者 | 项目没有公开 TCP/UDP 管理端口或远程命令 API | 未识别项目独立的直接网络入口；不评价宿主其他网络服务 |
| 普通本地用户/进程 | 可观察部分系统信息，权限允许时可写开发工作区 | 正常 root 专有运行目录形成边界；可写源码加上后续管理员授权执行形成安装风险 |
| 物理控制台访问者 | F9/F10、遗留救援会话、启动失败控制台 | 正常救援需要独立密码，但启动失败是另一条入口 |
| 恶意或被替换的 USB 存储 | 描述符、序列号、分区/LVM/文件系统元数据、读写响应与时序 | 防误接核验不构成设备真实性认证；下层驱动先于 Guard 处理设备 |
| 已取得宿主 root 的攻击者 | 配置、内核、映射、密码库及执行文件 | 项目无法提供对宿主 root 的隔离或可信证明 |

## 已有且应保留的保护

- **事件不是控制命令。** [core.cpp](../../guard/native/runtime/core.cpp) 的 `Events::wait()` 只把 netlink 发送端 `nl_pid == 0` 的相关事件作为唤醒依据，之后读取权威设备/映射状态；每批最多 64 条、单条缓冲 16 KiB，并合并检查。systemd 通知为 Unix socket 客户端，不是公共管理监听器。
- **没有把设备文本拼入 shell 执行。** `command()` 拒绝 NUL，使用 argv 和 `posix_spawnp`；恢复调用使用固定的绝对工具路径，子进程环境收窄，关闭无关 FD，保留恢复所有权锁。输出总量最多 1 MiB。超时不能保证终止内核 D 状态，但已有事务所有权处理。
- **运行状态主要位于 root 专有目录。** 本机 `/run/ram-rescue-guard` 与 `/run/ram-rescue-demo` 为 root 所有、0700。锁、临时事务文件与事件日志采用 0600 和最终路径 `O_NOFOLLOW`；事务文件原子替换。已安装管理包及父目录由 root 持有，不从开发工作区热加载常驻代码。
- **准入防止误接和实例混淆。** [admission.cpp](../../guard/native/runtime/admission.cpp) 联合 USB 信息、容量、分区、LVM/文件系统信息，并持有 FD、核对 dev_t/sysfs/diskseq；切换前再次检查，重复候选拒绝接入。
- **救援凭据不随公开构建包分发。** 初始镜像账户锁定；[prepare-shared-rescue](../../guard/integration/prepare-shared-rescue) 在启动后从宿主复制既有密码库，要求 root 所有、0600。
- **存在输入和资源上限。** 默认文本读取限制 64 KiB，日志及命令输出有界，服务有 CPU/内存 cgroup 限制。实验故障注入还受 lab 配置、启动参数及 QEMU DMI 标识门控；host 模式不读取故障注入配置。

以上控制降低误操作、竞态和部分滥用机会，不证明所有解析输入安全，也不限制取得进程执行权之后的全部行为。

## 优先项一：启动失败入口的认证缺口

**已静态确认的控制流：** [local-top](../../guard/integration/local-top) 第 13 行和 [init-bottom](../../guard/integration/init-bottom) 第 13 行的 `fail_closed()` 循环调用 initramfs-tools 的 `panic()`。本机 `/usr/share/initramfs-tools/scripts/functions` 第 44–96 行，在未设置 `panic=` 时运行交互式 root shell，不经过 F9/F10 密码认证。[install.py](../../guard/install.py) 的 `menu()` 生成的内核参数未设置 `panic=`。

本机核对的 `initramfs-tools-core` 为 `0.142ubuntu25.8`。以上证据来自项目源码与本机发行版脚本；本轮没有解包逐字比对已安装 initrd 内该函数，也没有通过故障启动复现现场控制台。

前提是保护启动进入该失败分支，并且攻击者能访问启动控制台。它继承发行版救援机制，不是本项目独有的通用 Linux 漏洞；但项目主动调用此路径，所以“失败后不继续启动未保护的根系统”不能被理解为“失败后不提供未认证的管理权限”。

**建议：** 首先在 QEMU 对这一入口做可重复验证，再明确默认失败行为和授权救援方式。不能只删除交互入口而放行未保护启动，也不应在本机未经验证地修改启动参数。F9/F10 的认证策略不能自动覆盖此路径。若威胁模型还包括修改引导参数或离线改盘，须另外说明引导链与存储保护的边界；本轮未审计 rEFInd、GRUB 密码或 Secure Boot 策略。

## 优先项二：高权限执行缺少影响范围限制

### 自动 Guard

[Guard unit](../../guard/integration/ram-rescue-guard.service) 主要设置启动顺序、共享 RAM 根目录、CPU 与内存配额，没有显式收窄 capabilities、系统调用、地址族和宿主可写范围。本机旧 Guard 与救援服务有效配置也显示 `NoNewPrivileges=no`、未启用 `ProtectSystem`/`ProtectHome`/`PrivateNetwork`/`PrivateDevices`，没有相应系统调用和地址族过滤。

[local-top](../../guard/integration/local-top) 将宿主 `/dev`、`/proc`、`/sys`、`/run` 绑定到 RAM 环境。`RootDirectory`/chroot 是断盘后的工具生存环境，不是限制宿主 root 的沙箱；Linux 对 chroot 的说明也明确不把它定义为安全隔离机制。[chroot(2)](https://man7.org/linux/man-pages/man2/chroot.2.html)

这意味着一旦 Guard 或其高权限子进程的漏洞被利用，影响可能扩大到整机。**本轮没有证实这种漏洞已经存在或可利用。** cgroup 配额只约束资源，不能代替访问控制。

**建议：** 分别列出早期激活、常驻恢复、只读介质解析、日志和人工救援需要的权限，先对自动执行路径做最小权限实验。`NoNewPrivileges` 只阻止执行新程序时取得额外权限，不会移除进程已有 root 权限；候选配置必须按实际能力验证。[systemd.exec(5)](https://man7.org/linux/man-pages/man5/systemd.exec.5.html)

不能直接启用 `PrivateDevices=yes` 隐藏真实块设备，或移除所有 `CAP_SYS_ADMIN`：当前 Linux DM ioctl 入口明确检查该 capability。挂载命名空间改变也可能破坏宿主挂载及共享锁的语义。应在 QEMU 覆盖启动、重连、超时、死亡接管和挂载后再选择限制。[Linux v7.0 dm-ioctl.c](https://github.com/torvalds/linux/blob/v7.0/drivers/md/dm-ioctl.c)

暂不以新增常驻特权代理作为默认方案；先用现有 systemd/内核机制验证可行的收缩，只有确有收益时才引入新的 IPC 与职责边界。

### F9/F10 人工救援

[build.py](../../ram-rescue-demo/build.py) 将 `rescue` 定义为 UID **0**；[session.sh](../../ram-rescue-demo/src/session.sh) 启动交互 shell。这是整机 root 授权，不是普通“root 组用户”，也不是隔离虚拟机。

正常登录使用独立救援密码。安装器目前只校验非空及两次一致；项目未实现空闲会话退出或与桌面锁联动。遗留已登录控制台和密码泄漏的后果与完整 root 登录相同。BusyBox 登录/监督循环已有失败延迟，不能据此称为没有任何重试节制，也不能视为完善的认证策略。

**建议：** 明确这项授权，评估独立终端会话策略，保留断盘时的离线可用性。人工完整救援与自动 Guard 应分别制定权限策略，不为了自动服务加固而不加区分地削减用户主动授权的救援能力。

## 优先项三：设备身份与不可信解析输入

VID/PID、序列号、分区 UUID、LVM 标识及布局都是设备可以提供或复制的数据。能模拟描述符并复制登记元数据的设备，在原盘消失后可能通过全部现有身份核验；diskseq 证明的是设备实例连续性，不是密码学意义的原盘身份。核验不覆盖所有数据，恶意设备还可在核验后改变响应。Linux USB 授权文档也提醒设备描述信息可以被伪造。[USB authorization](https://docs.kernel.org/usb/authorization.html)

因此必须把当前能力描述为**防止误接、识别登记信息与实例**，不能宣传为防克隆盘、恶意固件或 BadUSB。伪造数据被接受可能污染恢复结果；两个相同身份候选会使恢复安全拒绝并最终超时。这是可达的完整性/可用性边界，不等于已经证明代码执行攻击。

在最终接入之前，`blkid`、LVM 也已经解析候选盘元数据。`--readonly` 减少写盘副作用，不能防止解析器漏洞；目前 helper 启动路径未单独降 UID 或安装独立 seccomp。内核 USB/SCSI 层更早就接触设备，因此 Guard 无法作为整个 USB 栈的防火墙。

**建议：** 保留最终核验；为设备信息、异常 JSON/helper 输出和事件字段增加边界/恶意输入测试，评估只读解析 helper 的权限隔离。若未来要防范有意伪造硬件，单独制定威胁模型并评估已有 Linux USB 授权或可信存储机制，不把再加一个可复制 UUID 当成认证。当前不据此扩展 LUKS 等未支持拓扑。

## 优先项四：配置路径、安装与冻结依赖

### 配置和状态的权限前提

`read_text()` 当前跟随符号链接，未统一核对读取对象的 owner/mode；`O_NOFOLLOW` 只限制最终路径元素，不能替代父目录保护。正常 root 专有目录下，未发现普通用户直接控制这些路径的证据；如果管理员把配置或父目录交给普通用户写入，这一假设失效。

journal 的 SHA-256 和 `INVOCATION_ID` 用于一致性及运行归属，不是秘密口令或 MAC。建议在特权入口统一校验配置、状态和父目录的可信属性，并测试错误 owner/mode、符号链接和路径替换。不要宣称已有任意用户提权漏洞，也不要把散列字段当成权限边界。

### 安装执行体与来源信任

首次安装和部分升级操作会以 root 执行开发工作区里的 Python 脚本，并在入口导入同目录模块。本机源码及相关目录由开发用户持有、可写。具备工作区写权限的恶意进程如果先篡改脚本，管理员随后授权执行时就可能执行这些代码。

这需要“可写源码被改动”和“之后发生特权执行”两个前提，不能描述为普通用户随时能够直接提权。现有 root 所有的版本化已安装包提供了更好的边界，应在安装流程中延续。

构建清单、VM 报告与镜像散列证明**给定材料相互一致**。若攻击者可以同时改动执行体、镜像及其清单，散列本身不认证发布者。建议固定可信、root 所有的安装执行体；对外分发时明确可信来源和独立验证方式。把任意文件简单复制到 root 目录并不会追溯证明来源可信。

### 冻结工具/库的修补闭环

[native_payload.py](../../guard/native_payload.py) 将依赖复制进救援包；RAM 与 initrd 中的副本不会随宿主 `apt` 更新自动改变。需要重新构建、部署并进入新运行环境，不能用宿主包已更新证明冻结副本已修补。本轮未进行 CVE 清单审计，未判定存在某个已知漏洞。

建议构建时记录依赖版本/散列，在升级和按需 `doctor` 时核对；不新增后台更新轮询或自动联网更新器。

## C++ 构建与测试边界

实际候选 ELF（散列见部署记录）已观察到 PIE、GNU_RELRO、BIND_NOW、非执行 GNU_STACK，以及栈保护和 fortified 函数符号，不能说当前二进制没有基础防护。但 [build_runtime.py](../../guard/native/build_runtime.py) 尚未独立于发行版编译器默认值显式约束、验收这些属性。

已有核心、控制器与准入单元检查通过 ASan/UBSan 等检查，见 [迁移报告](../2026-10-02/CPP-MIGRATION.md)。这是既有证据，本轮没有重跑，也不等于恶意输入模糊测试。建议将构建防护检查和针对性 fuzz 纳入 CI；sanitizer 不必进入常驻生产进程，避免用线上资源换取开发期检测。
