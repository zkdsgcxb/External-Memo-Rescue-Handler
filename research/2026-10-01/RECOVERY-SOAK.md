# 十轮共同断联恢复与内存稳定性

## 最终优化与复验

**保留完整恢复流程后，十轮恢复结束的三个 Guard 合计 PSS 从 50.290 MiB 降至 38.562 MiB，减少 11.728 MiB，约 23.3%。** 同时 cgroup current 从 57.359 MiB 降至 45.238 MiB，减少约 21.1%。健康初始内存基本相同；这是降低恢复后保留的内存，没有把减少虚拟地址预留冒充物理内存收益。

| 检查点 | 原实现 PSS MiB | 最终实现 PSS MiB | 原实现 cgroup current MiB | 最终实现 cgroup current MiB |
| --- | ---: | ---: | ---: | ---: |
| 首次断联前 | 37.921 | 37.889 | 44.359 | 44.453 |
| 首次恢复后 | 50.149 | 38.426 | 56.957 | 45.062 |
| 第十次恢复后 | 50.290 | 38.562 | 57.359 | 45.238 |

修改只有 `owned_operation.py` 的异常诊断格式化：保留异常类型、消息、最多 16 帧的文件名/行号/函数名，并限制各字段字节数；取消源代码行读取、缓存和用于精细插入符显示的解析。它仍返回原有 `type/message/traceback` 字符串字段，未改变准入、所有权、超时、回调或 FD fence。

原来的 `traceback.format_tb` 在第一次拒绝尚未出现的 USB 路径时导入 `traceback/linecache/tokenize/textwrap/ast` 等模块。本项目 RAM 工具构建明确排除 `__pycache__` 和 `.pyc`，首次导入还会编译源码，留下额外的解释器/分配器工作内存。这里的优化直接避免不需要的源代码解析；没有调整 malloc arena、线程栈、GC 或强制回收策略。

先用三个全新进程对照验证：原格式化路径首次错误增加 PSS 约 0.884 MiB，最终路径约 0.021 MiB，最终路径没有新导入模块。该小实验使用本机标准库缓存，数值不能直接代替 RAM 客户机测试；原始结果保存为 [error-memory.json](../../lab/results/2026-10-01-error-memory.json)，脚本通过固定 Git 基线及前后源码 SHA 使对照可重跑。

随后在同一套完整 Ubuntu QEMU 流程重做十轮共同断联。**19/19 验收再次全部通过**；三个控制器、原工作进程与挂载保留、数据摘要匹配、FD/线程数稳定、源码/只读种子不变、正常关机和离线 ext4/FAT 检查均通过。三个实际 runtime 中前后唯一变化的文件及 SHA：

| 文件 | 原实现 SHA-256 | 最终实现 SHA-256 |
| --- | --- | --- |
| owned_operation.py | `d06d8da0d7203e52fbb761d704aab882c630a53b4676dd9050fe5933a0fa9d90` | `1c3febc34cd036d5e921ab7f49bf11eab9b85ee1085c1a7c21764d7270a4daf1` |

最终完整结果：`lab/work/soak-1001-052736-895957/report.json`；可提交摘要：[soak-final.json](../../lab/results/2026-10-01-soak-final.json)。原始基线与其摘要保留。最终实现的 26 项 OwnedOperation 测试通过，新增检查覆盖诊断过程中不导入模块、不读源代码、深层 traceback 和长 UTF-8 元数据边界；原有异常 `__str__` 失效、回调清理和 fence 生存期测试继续通过。

最终十轮主机观察到全部恢复的时间为 3.538～3.856 秒；原十轮为 3.120～3.896 秒。周期累计 Guard CPU 时间由 1.800 秒变为 1.638 秒，但这些周期还包含每轮稳定等待，不能替代独立性能报告的 CPU 峰值或因果延迟比较。最终客户机仍有 6 条原始 sdX I/O error，受测应用无 I/O 错误，文件系统检查干净；不把下层错误日志隐藏成“没有错误”。

## 优化前的稳定性基线

完整 Ubuntu VM 中，对保护根盘、额外 ext4 和 FAT32 数据盘同时断开/接回，连续进行 **10 轮、共 30 次设备断联**。三个原 Guard、三个原工作负载及原挂载保持不变，所有确认写入的最终内容匹配，19 项验收通过，正常关机后的 ext4/FAT 离线只读检查均返回 0。

首次恢复使三实例合计的进程 PSS 从 **37.921 MiB 增至 50.149 MiB**；第十轮为 **50.290 MiB**。后五轮的进程 RSS 合计和 cgroup 匿名内存计数完全不变，三个控制器始终各有 7 个 FD、1 个存活线程；首次恢复增加的映射数量此后没有继续增加。这支持“首次故障后的工作内存进入稳定区间”，没有观察到随每次恢复持续累积的明显资源泄漏。十轮试验不能证明任意运行时长下都没有泄漏。

## 口径与可复查材料

- 命令：`python3 lab/soak_guard_probe.py --cycles 10`。
- 原始结果：`lab/work/soak-1001-050658-817605/report.json`。
- 可提交的完整检查点摘要：[2026-10-01-soak.json](../../lab/results/2026-10-01-soak.json)。
- Ubuntu 24.04.5、Linux `7.0.0-34-generic`、x86-64 KVM；使用当前源码，根盘及数据盘实际运行的 RAM runtime 摘要前后一致。只读种子和源码指纹均保持不变。
- 沿用原来的 CPU 配额，不更改主机或客户机生产策略，不调用 GC、malloc trim 或其他主动回收手段。
- 每轮三个实例均 ready、工作负载继续推进之后等待 0.75 秒，再读资源检查点。检查点用于判断恢复后的保留内存，**不是恢复时的内存或 CPU 峰值**。
- cgroup 合计只加“根盘 service”与“整个数据 slice”两个互不重叠的组，包含各自后代，不再重复加两个数据 service。观察进程及工作负载不在此口径内。
- PSS/RSS 单独从这两个组下的进程读取，记录 PID/start_ticks；每个检查点确认仅存在三个控制器，没有残留辅助进程。RSS 相加会重复计算共享页，不能把它当作实际独占物理内存。
- cgroup `memory.current` 包括所计费的匿名页、文件页及内核开销；它与 PSS 的含义不同。`memory.stat` 的 shmem、slab、pagetables 等子项也不能重复加到总量里。

## 首次增加的内存来自哪里

| 合计计数 | 断联前 MiB | 首次恢复后 MiB | 第十次恢复后 MiB |
| --- | ---: | ---: | ---: |
| cgroup 匿名内存 | 28.969 | 41.215 | 41.344 |
| cgroup 文件页 | 1.105 | 2.211 | 2.285 |
| cgroup 内核内存 | 13.641 | 13.020 | 12.828 |
| 进程 PSS | 37.921 | 50.149 | 50.290 |

首次增加约 12.2 MiB 的 PSS 与匿名内存增量接近，所以**不能只解释为页缓存增加**。按 `/proc/<pid>/smaps` 分类，三个进程的 `[heap]` PSS 基本不变；增加主要位于无文件名的匿名映射中。

每个控制器的匿名虚拟映射总大小约从 5.703 MiB 增至 150.711 MiB，此后完全不变。对应匿名 PSS 只增加约 4 MiB，而非 145 MiB：大部分地址空间没有实际驻留页。这个布局与线程运行后保留的分配器区域、线程栈缓存一致，但仅凭 smaps 不能证明具体由哪一种分配器创建，不把推测当作已定位的原因。

首次恢复后的映射数量为根盘 124、ext4 124、FAT32 125；十轮结束仍是这三个数字。各自 FD 数始终为 7，检查点线程数始终为 1。第 1 到第 10 轮进程 PSS 合计仅多 0.141 MiB，匿名内存多 0.129 MiB，文件页多 0.074 MiB；后五轮匿名内存/RSS 已完全持平，PSS 仅在约 0.051 MiB 范围内变化。PSS 还会受到组外进程共享页归属比例的影响。

这组基线先排除了明显随恢复轮次累积的泄漏。随后针对首次异常诊断的一次性开销实施了上面的局部优化；以下保留数据不作为最终实现的占用数字，也没有通过不受控的强制回收措施掩盖工作内存。

## 错误与一致性边界

客户机日志包含 **12 条消失的原始 `sdX` 设备上的 I/O error**。这是下层断联时出现的真实块请求错误，不能删掉日志或声称“内核完全没有错误”。但本次三个原工作负载都没有收到 I/O 错误、确认写入内容一致，未出现 `WARNING:` 或 `EXT4-fs error`，两个额外文件系统离线检查干净。证据说明本次下层错误没有破坏受测上层工作负载的连续性，不承诺所有驱动和全部错误都能被相同方式吸收。

数据工作负载持续保留文件描述符，每次写入执行 fsync，再以 O_DIRECT 读回。根盘工作负载保留原进程身份并校验确认写入前缀。每轮都核对原挂载、boot ID、PID 1、控制器 PID/start_ticks 与 owner epoch，以及准确递增的恢复次数。轮转日志同时读取当前和前一文件，避免把日志轮转误认为缺失恢复事件。
